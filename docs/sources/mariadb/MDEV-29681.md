# MariaDB: MDEV-29681

Source: https://jira.mariadb.org/browse/MDEV-29681

- Summary: Server crashes when optimizing SQL with ORDER BY.
- Affected versions: 10.6.7, 10.6.10, 10.3 to 10.9.
- Fix versions: 10.4.33, 10.5.24, 10.6.17, 10.11.7, 11.0.5, 11.1.4, 11.2.3,
  11.3.2.
- Example of the ticket (comment of 2022-10-04):

  ```sql
  (SELECT * FROM t1 JOIN t2 ON a=b LIMIT 5) ORDER BY a=16;
  ```

- Message of the fix (commit 15ba38083837013d0795a425a403ed9b71d9b750, in
  a comment of 2023-11-05):

  > When parsing statements like (SELECT .. FROM ..) ORDER BY <expr>,
  > there is a step LEX::add_tail_to_query_expression_body_ext_parens()
  > which calls LEX::wrap_unit_into_derived(). After that the statement
  > looks like SELECT * FROM (SELECT .. FROM ..), and parser's
  > Lex_order_limit_lock structure (ORDER BY <expr>) is assigned to
  > the new SELECT. But what is missing here is that Items in
  > Lex_order_limit_lock are left with their original name resolution
  > contexts, and fix_fields() later resolves the names incorrectly.
  > [...]
  > This commit fixes the issue by changing context for Items in
  > Lex_order_limit_lock after LEX::wrap_unit_into_derived().

Consulted for the outer `ORDER BY` of a query between parentheses with an
`ORDER BY` or a `LIMIT` of its own (`crates/probe/cases/parenthesized-order.sql`,
measured on each local image, 10.5.29 to 11.8.9): before the fix, a key
other than a name alone or a position reads its names in the context of the
query between parentheses, and sorts the rows in no defined order once that
query is materialized (`LIMIT`, `DISTINCT`, `GROUP BY`); an expression of
the alias of a window function stops the server. The defect on 10.6.16,
10.7.8 to 10.11.6, 11.0.2 to 11.0.4, 11.1.2, 11.1.3 and 11.2.2; fixed on
10.5.29, 10.6.17, 10.11.7, 11.0.5, 11.1.4 and 11.2.3, as the fix versions
of the ticket say. 10.7 to 10.10 were never fixed.
