# Implementation plan of the dialects

This document orders the work on the dialects of the v1, step by step: the parsers of the input dialects (MySQL, MariaDB, PRQL), the logical plan, the emitters of the output dialects (MySQL, MariaDB), the audit of the transpilation and the beautifier. The decisions themselves are in `docs/V1.md` (sections 2.1, 2.2, 2.9 and 2.10) and in `docs/QUESTIONS.md`; this document cites them and says in which order they are built.

Each step ends on a state usable end to end, with its tests and its documents updated. The **[to decide]** marks and the numbered points ("point 39") refer to the open points of `docs/QUESTIONS.md` (section 5).

## 1. Decisions the plan relies on

- **Input dialects** of the v1: MySQL, MariaDB, PRQL, plus "Selon source de données" (according to the data source), which is the native SQL of the target. The choice is a setting of the user's profile, "Dialecte préféré" (Preferred dialect), which the editor tab can override (`docs/V1.md`, section 2.1).
- **Versions**: the user chooses the version of the dialect they write in (MySQL 8.0.19, MariaDB 10.6...). The versions offered are those where the dialect changed (additions, removals), listed with their changes in the registry of the versions (step 2). With "Selon source de données", the version is the server's.
- **Each dialect stays in its domain**: a parser accepts only the SQL valid in its dialect and its version, and an emitter writes only SQL valid in the target dialect and version. Prisme adds no extension to a dialect: `ORDER BY a NULLS LAST`, absent from MySQL, is an error of the MySQL parser, even though the plan can represent it and the MySQL emitter can emulate it for another input dialect.
- **Output dialects** of the v1: MySQL and MariaDB, the engines Prisme has a connector for. PostgreSQL, SQLite and DuckDB come with their connectors (`docs/V1.md`, section 4).
- **Transpilation**: parser (input dialect to AST), plan builder (AST to logical plan), emitter (logical plan to output dialect). The logical plan is the single pivot; a query whose input dialect is the output dialect goes through it too.
- **Everything is written by Prisme**: one parser per dialect, the plan builders, the emitters, the PRQL parser (the whole language, after the PRQL book, https://prql-lang.org/book/). `sqlparser-rs` becomes a dev-dependency, an oracle of the tests.
- **Scope**: the DML (`SELECT`, `INSERT`, `UPDATE`, `DELETE`), plus the catalog and session statements (`SHOW`, `DESCRIBE`, `EXPLAIN`, `USE`, `SET`, queries on the catalog of the engine). DDL is set aside.
- **Never a silent approximate translation** (rule 2 of `CLAUDE.md`): each construct is translated natively, emulated by Prisme (result type and use of indexes kept, except the position of NULLs in a sort, whose loss of index is reported), or refused with an explicit error. A catalog or session statement is translated as far as needed; when the target gives less than the same request written in its own dialect, the report states the loss of precision.
- **Audit**: every rewrite and every emulation is listed, with its position in the input; every untranslatable construct is listed with its error.
- **Settings of the server**: a result that depends on the settings of the server or of the data (collation, `sql_mode`, time zone) follows the target server. The transpiler translates the language and neither emulates nor reports these settings: on the same rows, `WHERE v = 'a'` keeps `'a '` on MariaDB (PAD SPACE collation by default) and leaves it out on MySQL 8 (`utf8mb4_0900_ai_ci`, NO PAD) (`docs/FEDERATED.md`, section 6).
- **Beautifier**: generated from the plan, comments kept (`docs/V1.md`, section 2.9).

## 2. Target architecture

### 2.1 Crates and modules

| Place | Role |
|---|---|
| `crates/types` (new) | Internal types with their nullability (`docs/FEDERATED.md`, section 6). |
| `crates/plan` (new) | Nodes of the logical plan (`docs/FEDERATED.md`, section 5.1) and their expressions, with the origin of each node (section 2.3 below). Depends on no dialect. |
| `crates/dialects` | Lexers, ASTs and parsers of the input dialects, plan builders, emitters of the output dialects, function catalog, transpilation report. |
| `crates/splitter` | Unchanged at first; later on the lexer of the dialect (`docs/QUESTIONS.md`, point 30). |
| `crates/server` | Chooses the input and output dialects, transpiles, sends the report, runs the output. |
| `web/` | Choice of the dialect (profile, tab), preview of the transpilation, highlighting per input dialect. |

Proposed modules of `crates/dialects`:

- `versions`: registry of the changes of each dialect, version by version (constructs, keywords, functions), source of the versions offered to the user;
- `lexer`: lexer of the SQL dialects, set by the dialect, its version and the SQL mode;
- `sql::ast`: AST common to the SQL dialects, with the nodes specific to a dialect;
- `mysql`: grammar common to MySQL and MariaDB; `mariadb`: what only MariaDB has;
- `prql`: lexer, AST and parser of PRQL;
- `build`: plan builders, from the SQL AST and from the PRQL AST;
- `emit`: SQL emitter common to the output dialects, one module per output dialect for its differences;
- `catalog`: functions of each dialect and version (native, emulated, unsupported);
- `transpile`: entry point and report.

The modules become crates if the build time requires it (measures in `docs/PERF.md`).

### 2.2 Data flow and report

The processing of a query is the diagram of `docs/V1.md`, section 2.10. Main types, as a sketch:

```rust
/// Dialect the user writes in: the native SQL of the target, or a language with its version.
pub enum InputDialect { Source, Chosen { language: Language, version: Version } }

/// Language of an input dialect.
pub enum Language { MySql, MariaDb, Prql }

/// Dialect of the server that runs the query, with its version.
pub struct OutputDialect { pub engine: Engine, pub version: Version }

/// Result of a transpilation, sent to the interface before running.
pub struct Transpilation {
    /// Query in the output dialect.
    pub sql: String,
    /// Rewrites, emulations and losses of precision, each with its rule and its position in the input.
    pub steps: Vec<Step>,
    /// Untranslatable constructs, each with its position and its reason.
    pub errors: Vec<Untranslatable>,
}
```

Each rule of translation (structural rewrite or function of the catalog) has a stable identifier, cited by the report and by its test (rule 8 of `CLAUDE.md`). The report is a type generated for the interface by `ts-rs`.

### 2.3 Origin of the plan nodes

Each node and each expression of the plan keeps its **origin**: its position in the input (for the audit, the comments and the errors) and the syntactic form written by the user when several forms have the same meaning (`VALUES ROW (...)` or `VALUES (...)`, `<=>` or `IS NOT DISTINCT FROM`, `LIMIT a, b` or `LIMIT b OFFSET a`, alias with or without `AS`). The emitter writes the original form when the output dialect accepts it; otherwise it writes another form and records a step in the report. Hence:

- a query transpiled to its own dialect comes out with its forms, and its report holds only the rewrites for optimisation;
- every difference between the input and the output is a step of the report, none is silent.

Decided (point 39), with a reservation: the principle can evolve. A rewrite for optimisation (a range in place of a function, to keep the use of an index) changes the form even towards the same dialect; it is then a step of the report, like any other difference.

Decided autonomously, to be reviewed by the maintainer:

- the lexical differences are not steps of the report: case of the keywords, spaces and line breaks, quote character of an identifier, synonyms of an operator (`!=` and `<>`, `&&` and `AND`, `%` and `MOD`, `!` and `NOT`), canonical spelling of a literal of the same value. The emitter writes a literal as in the input when the output reads it the same way (same SQL mode for the quotes and the backslashes);
- in the MySQL family, a column without alias takes its name from the text of its expression: when the text written differs from the text read (`a+1` written `a + 1`), an alias keeps the name, with a step of the report;
- the comments are written again before the first construct that follows them in the input.

### 2.4 Invariants, checked at each step

1. **Round trip**: for each dialect and each query of the corpus, parsing the output again gives the same plan (fixpoint), and the report of a transpilation to the same dialect holds only rewrites for optimisation.
2. **Same results**: on a real server, the query and its transpilation return the same rows (conformance suite).
3. **Comments**: the same comments, with the same text, before and after.
4. **No silent approximation**: every difference between input and output comes from an identified rule, with its test and its line in the report.
5. **Oracle**: on the corpus, the parser of Prisme accepts and refuses the same queries as `sqlparser-rs`, and the trees agree, except for listed differences (MariaDB, versions, known gaps of `sqlparser-rs` such as `JSON_TABLE`). The trees are compared through a canonical printing: `Display` of `sqlparser-rs` on one side, a test printer of the AST of Prisme in the same form on the other.
6. **Performance**: time linear in the size of the query; budget measured on the long single-line query of `docs/PERF.md`.

## 3. Steps

### Step 0. Decisions before the code

Settled before step 1, as the types and the plan depend on them, from the behaviour measured on MySQL 8.4.11, MariaDB 10.6.28 and MariaDB 11.8.9. Done.

- NULL, points 1 to 6 of `docs/FEDERATED.md`, section 7 (`docs/QUESTIONS.md`, point 12): the two equalities, three-valued logic, joins, set operators, aggregation, sorting;
- the internal types of the v1 (`docs/FEDERATED.md`, section 6): integers (unsigned `BIGINT` included), exact decimals, booleans, strings, dates, JSON.

### Step 1. Types and plan

- `crates/types`: integer types (sizes, signed or not), exact decimal, floating point, string, binary, boolean, date and time types, JSON, unknown type; nullability. Conversion from the column types the MySQL connector reads (`crates/connectors/src/mysql/column_type.rs`).
- `crates/plan`, the nodes the DML needs: `Scan`, `Values`, `Filter`, `Project`, `Extend`, `Aggregate`, `Sort`, `Limit` (count and offset), `Distinct`, the joins (inner, left, right, cross; full later), the six set operations, common table expressions (recursive included), window functions; `Insert`, `Update`, `Delete` at the root; for step 8, the relations of the catalog of Prisme, read by `Scan`, and the session nodes (`Use`, `Set`, `Explain`). Expressions: column references, literals, operators with explicit semantics (comparison equality and identity equality), calls to functions of the catalog, `CASE`, `CAST`, subqueries (scalar, `IN`, `EXISTS`).
- Origin of the nodes (section 2.3); output schema of each node. The column types come from the catalog of the connection, read on demand for the tables of the query, just before transpiling, on the connection of the session (`SHOW COLUMNS` also sees its temporary tables); the type of an expression the plan cannot derive is asked to the server through the metadata of a prepared statement, without running it (point 44).
- Tests: construction, output schemas, nullability rules decided in step 0.
- Done when the plan represents by hand the queries of step 4.

Done: `crates/types` (types, values, `i128` integers, decimals as exact text), `crates/plan` (nodes, expressions typed with their nullability, origin), conversion of the result types of the MySQL connector (`plan_types`), and the queries of step 4 built by hand (`crates/plan/tests/example.rs`). Left to the steps that need them: the relations of the catalog of Prisme (step 8); the full outer join, `USING` and `NATURAL`, row constructors (`(a, b) IN (...)`) and multi-table writes, with the complete grammar (step 5); the other written forms, with the parsers that read them.

### Step 2. Registry of the versions

The user chooses the version of the dialect they write in (point 43): Prisme knows the period of validity of each keyword, construct and function.

- **Content**, per dialect: each construct of the grammar (`WITH`, `WITH RECURSIVE`, `VALUES` and `TABLE` statements, row alias of `INSERT ... ON DUPLICATE KEY UPDATE`, `RETURNING`...), each keyword and each function, with the version it appeared in (`since`), the version it was removed in (`until`) and its source (reference manual or release notes of the engine); a construct can add a comment (`comment`), its context: what it does, how it was established. A construct that several branches received apart, as a fix of patch versions, has an entry per period, in order: accepted within one of them. The keywords followed this model first; the registry extends it to the constructs and the functions.
- **Examples**, each confirmed by its source when it enters the registry: common table expressions, recursive included, from MySQL 8.0.1; `VALUES` and `TABLE` statements from MySQL 8.0.19; `INTERSECT` and `EXCEPT` from MySQL 8.0.31; the `UUID` type from MariaDB 10.7.
- **Versions offered** to the user: those where the dialect changed (a version that adds or removes something), derived from the registry. The registry starts with the most recent and most widely used versions, MySQL 8.0 and later, MariaDB 10.6 and later; older versions can be added afterwards (point 51).
- **Storage**: a single data file per dialect, `crates/dialects/reference/<dialect>.yaml`, the only source of what Prisme knows of the dialect (keywords, constructs, then functions), edited directly, read in the diffs and embedded in the executable (point 50). A fact that depends on the version carries its period (`since`, `until`) and cites the document of that version that attests it.
- **Use**: the lexer and the parser accept a keyword or a construct only within its period, for the chosen version, otherwise an explicit error ("`VALUES` statement: from MySQL 8.0.19, chosen version 8.0.18"); the emitter checks the version of the server the same way; executable comments are resolved against the chosen version (point 41). Each construct added to a parser in the next steps enters the registry with its versions.
- **Tests**: each entry has its test (accepted from `since`, refused before); the entries are checked on real servers of the versions available in Docker (ignored tests).

Done for the constructs (`crates/dialects/src/versions.rs`, `crates/dialects/reference/*.yaml`): floor at the first GA release of each series, MySQL 8.0.11 and MariaDB 10.6.3 (release notes); the constructs of the MySQL family that depend on the version, each with its source; the versions offered derived from them; the messages of refusal. The built-in functions have their periods in the same files (step 7), which add the versions where a function appears or disappears to the versions offered. Each file gives the last version inspected of each section (`inspected`), up to which the section is complete: an update starts from the release notes of the later versions. The checks on real servers go with the conformance suite (steps 4 and 6), on the versions available in Docker.

### Step 3. Lexer of the MySQL family

- Tokens with their position (byte offsets, line and column), comments kept as tokens with their position.
- Set by the dialect (MySQL or MariaDB), its version (registry, step 2) and the SQL mode read on connection (`ANSI_QUOTES`, `NO_BACKSLASH_ESCAPES`, `PIPES_AS_CONCAT`; `docs/QUESTIONS.md`, point 30).
- Executable comments (`/*! ... */`, `/*!80000 ... */`, `/*M! ... */`) are code for the server, depending on its version. Prisme resolves their condition (version of the server towards the same dialect, version of the input dialect otherwise, point 43): the content is then code, given to the parser and translated with the rest of the query, or a plain comment. A content that cannot be translated is reported (point 41).
- Tests: units, oracle (tokens of `sqlparser-rs` on the corpus, listed differences aside), performance budget.

Done (`crates/dialects/src/lexer.rs`): tokens with their position in bytes, line and column computed for the messages (`LineIndex`); comments as tokens; SQL mode read from `@@sql_mode` (`SqlMode`, combination modes expanded); executable comments resolved against the version given by the caller, six-digit versions read as MySQL 8.0.34 and later do (six digits followed by a whitespace) and as MariaDB does (six digits). Oracle: the tokens of a corpus cut like those of `sqlparser-rs`; listed difference: an unquoted user variable keeps its dots (`@a.b`), as in MySQL. Budget: 1 MB on a single line, about 240,000 tokens, in a fraction of a second.

### Step 4. First vertical slice: the example of the dialects

Goal: `WITH ds (c) AS (VALUES ROW (123), ROW (234), ROW (345)) SELECT * FROM ds`, written in MySQL, runs on MariaDB as `WITH ds (c) AS (VALUES (123), (234), (345)) SELECT * FROM ds`, and the report shows the rewrite with its position.

- **Parser**: minimal MySQL grammar: `WITH` with a column list, `VALUES` and `VALUES ROW`, `SELECT` (columns, `*`, expressions with literals, arithmetic, comparisons, `AND`, `OR`, `NOT`), `FROM` a table or a common table expression, `WHERE`, `ORDER BY`, `LIMIT`. Any other construct gives the error "not supported yet by the parser of Prisme", with its position.
- **Plan builder** and **emitters** MySQL and MariaDB for this subset, aware of the versions: the `VALUES` statement from MySQL 8.0.19, table value constructors in every MariaDB version covered (10.6 and later).
- **Entry point** `transpile(input, input_dialect, output_dialect) -> Transpilation`; the current `Dialect` enum (MySQL, MariaDB) becomes the output dialect, with the server version.
- **Server**:
  - profile setting, migration `users.preferred_dialect` (`TEXT NOT NULL DEFAULT 'source'`: `source`, or a dialect with its version, such as `mysql 8.0.19`, checked by the server against the registry);
  - override per editor tab, migration `editors.dialect` (`TEXT NOT NULL DEFAULT ''`, same values, the empty string meaning "the value of the profile");
  - route `POST /api/transpile` (preview without running);
  - when the input dialect is not "Selon source de données": transpilation, then the current read / write classification and row limit applied to the output (temporary, until step 10), then running; the report goes with the result. "Selon source de données" keeps the current path until step 10, so that the default setting changes nothing.
- **Interface**: choice of the dialect and of its version in the profile dialog and on the editor tab (PRQL offered from step 9), transpiled query and report in the result tab, preview button. Light and dark modes checked (rule 10 of `CLAUDE.md`).
- **Tests**: units, round trip, route, interface (Vitest), and on a MariaDB server (Docker): the MySQL query of the example returns its three rows.

Done: transpiler (`crates/dialects`: `sql`, `build`, `emit`, `report`, `transpile`), server (`crates/server/src/transpilation.rs`) and interface (list of the dialects in the profile and on each editor, report folded above the result, preview window; light and dark modes checked). Decided autonomously, to be reviewed by the maintainer:

- the columns of the tables come from the metadata of `SELECT * FROM t`, prepared on the connection that runs the query, without running it: its temporary tables are seen, a view is not computed, and the types are those the connector already reads from a result (`plan_type`);
- the interface sends the dialect with each run (`dialect` of the `run` message), resolved from the tab and the profile; the server checks it against the registry;
- the report comes in a `transpiled` message, before the result, and is saved with it;
- the preview (`POST /api/transpile`) reads the columns on a new connection placed on the database of the session: the temporary tables of the session are not seen there;
- the editor highlights and analyses the text in the dialect it is written in, with its version; the syntax errors underlined as you type still come from `sqlparser-rs` until step 10, the parser of Prisme giving its own error when the query runs.

### Step 5. Complete MySQL DML grammar

- `SELECT`: options (`DISTINCT`, `DISTINCTROW`, `HIGH_PRIORITY`, `STRAIGHT_JOIN`, `SQL_NO_CACHE`, `SQL_CALC_FOUND_ROWS`...), all the expressions with their precedence (`DIV`, `MOD`, `XOR`, `<=>`, `REGEXP`, `SOUNDS LIKE`, `MEMBER OF`, `->`, `->>`, `COLLATE`, `BINARY`, `:=`, `@variable`, `@@variable`, `INTERVAL`, `CASE`, `CAST`, `CONVERT`, `EXTRACT`; literals with charset introducers, hexadecimal and bit literals, `DATE '...'`), `FROM` (all the joins, `USING`, `NATURAL`, derived tables, `LATERAL`, `JSON_TABLE`, index hints, `PARTITION`), `GROUP BY ... WITH ROLLUP`, `HAVING`, `WINDOW` and window functions, the forms of `LIMIT`, set operations with parentheses, recursive common table expressions, `TABLE t`, locking clauses (`FOR UPDATE`, `FOR SHARE`, `NOWAIT`, `SKIP LOCKED`, `LOCK IN SHARE MODE`), `INTO` (variables, `OUTFILE` and `DUMPFILE`, which are writes), optimizer hints `/*+ ... */`.
- `INSERT` and `REPLACE` (`VALUES`, `SET`, `SELECT`, `TABLE`, `ON DUPLICATE KEY UPDATE` with `VALUES()` or a row alias), multi-table `UPDATE` and `DELETE`, with `ORDER BY` and `LIMIT` (point 34).
- Type of a user variable (`@x`): read with `SELECT @x, @y` on the connection that runs the query, just before running it, after the previous queries of the batch; each query of a batch is therefore transpiled just before it runs (point 44).
- Constructs with no effect on the result (hints, options such as `SQL_NO_CACHE`) are annotations of the plan: written towards the same dialect, left out towards another one, with a step in the report (point 42).
- **Corpus**: queries written for Prisme, grouped by family, each with its expected status per dialect and version, in `crates/dialects/tests/corpus/`; the queries of the conformance suite are part of it. No copy of the test suites of MySQL or MariaDB (GPL license).
- **Tests**: oracle `sqlparser-rs`; acceptance confirmed by the real server (`PREPARE` on a test schema, Docker); round trip with the same results on MySQL.
- Done when the whole MySQL DML corpus passes the invariants of section 2.4.

Progress, first increment: sources, set operations and subqueries. Read, built and written towards MySQL and MariaDB: joins (comma, `JOIN`, `INNER`, `CROSS`, `STRAIGHT_JOIN`, `LEFT` / `RIGHT [OUTER]`, `NATURAL`, `ON`, `USING`), sources between parentheses, derived tables (`LATERAL`, column list), `PARTITION`, index hints, set operations (`UNION`, `EXCEPT`, `INTERSECT`, with `ALL` / `DISTINCT` and parentheses), `TABLE t`, subqueries (scalar, `IN`, `EXISTS`, `ANY` / `SOME` / `ALL`, correlated), rows (`(a, b)`, `ROW(a, b)`). The grammar follows what MySQL 8.0.11 and 8.4, MariaDB 10.6 and 11.8 accept, measured on the servers:

- the comma joins loosest (`a, b JOIN c ON x` is `a, (b JOIN c ON x)`); a join reads its right side greedily; an inner join without condition whose right side is a join joins the leftmost table of that side (`a JOIN b JOIN c ON x` is `(a JOIN b) JOIN c ON x`); `LEFT` and `RIGHT` need `ON` or `USING`; `NATURAL` reads a single table; `STRAIGHT_JOIN` takes `ON` only;
- `USING` and `NATURAL` merge the columns of the same name: the merged column answers to its name alone and comes first in `*`, taken from the left side (from the right side for a right join, whose columns then come first); each side keeps its own column, reached by its qualifier, `t.*` included;
- `INTERSECT` binds tighter than `UNION` and `EXCEPT`; before MySQL 8.0.31, `INTERSECT` and `EXCEPT` are not reserved, hence aliases;
- `<=>` has no `ANY` or `ALL`; a row compares with `= ANY` and `<> ALL` only, the forms of `IN` and `NOT IN`; `ROW` holds two values at least.

New rules of the report: `table.select` (`TABLE t` written `SELECT * FROM t` towards MariaDB and MySQL before 8.0.19), `derived.columns` (column list of a derived table emulated by a common table expression towards MariaDB before 11.7.1), `set.nested` (set operation between parentheses as a right operand, emulated by a derived table towards MySQL before 8.0.31; an error when its columns have the same names), and the errors `set.operator` (`INTERSECT` and `EXCEPT` towards MySQL before 8.0.31), `derived.lateral` (towards MariaDB), `derived.outer-reference` (column of an enclosing query in a derived table, towards MariaDB and MySQL before 8.0.14), `join.kind` (semi-joins and anti-joins of other dialects). Decided autonomously, to be reviewed by the maintainer:

- the merged column of `USING` and `NATURAL` takes the type of the side it comes from, not null after an inner join; the side of an outer join that may find no match is nullable in the expressions of the query;
- `UNION DISTINCT` and `UNION`, `SOME` and `ANY`, `ROW(a, b)` and `(a, b)` are lexical synonyms: the plan does not keep them;
- `INTERSECT`, `EXCEPT`, `LATERAL` and the outer references of a derived table are explicit errors towards the outputs without them, until their emulations (`EXISTS` with `<=>` for `INTERSECT` and `EXCEPT`, for example) are written;
- subqueries of several columns compared with a row (`(a, b) = (SELECT x, y ...)`) are refused by the builder, "not supported yet"; so is `JSON_TABLE` by the parser. The several levels of `ORDER BY` and `LIMIT` of MySQL before 8.0.31 are not modeled.

Progress, second increment: function calls, aggregation and windows. Read, built and written towards MySQL and MariaDB: function calls (`f(a)`, `db.f(a)`, a reserved word before `(` such as `LEFT`), aggregate functions (`COUNT(*)`, `DISTINCT`, `GROUP_CONCAT` with `ORDER BY` and `SEPARATOR`), `GROUP BY` (expressions, positions, aliases, `WITH ROLLUP`), `HAVING`, window functions (`OVER w`, `OVER (w ...)`, `PARTITION BY`, `ORDER BY`, `ROWS` / `RANGE` frames) and the `WINDOW` clause. Measured on the servers:

- the names of some built-in functions touch `(`: `SUM (a)` calls a stored function, `COUNT (*)` is a syntax error (the list is in the function catalog, step 7);
- `GROUP BY` reads a column of the source before an alias of the select list (`SELECT x AS k ... GROUP BY k` groups on the column `k`), `HAVING` a grouping column first, `ORDER BY` an alias first (inside an expression, the paragraph of the aliases below); a key that reads an aggregate function is refused;
- `ORDER BY` with `WITH ROLLUP`: MySQL since 8.0.12, never MariaDB;
- `OVER w` uses the window as defined, its frame included; a window that completes another one (`OVER (w ORDER BY a)`, `WINDOW v AS (w ...)`) adds an order when `w` has none and a frame, never a partition, and `w` has no frame; MySQL reads the window a definition completes anywhere in the `WINDOW` clause, MariaDB before it;
- MariaDB computes `RANK`, `DENSE_RANK`, `PERCENT_RANK`, `CUME_DIST`, `LAG` and `LEAD` over an ordered window only, and its `LAG` and `LEAD` have no default value;
- types: `COUNT` is a `BIGINT` not null; `SUM` of an exact number is a `DECIMAL` of 22 more digits, `AVG` a `DECIMAL` of 4 more digits and 4 more of scale, both a `DOUBLE` otherwise; `MIN` and `MAX` keep the type; `BIT_AND`, `BIT_OR` and `BIT_XOR` are `BIGINT UNSIGNED` not null; the ranks are `BIGINT UNSIGNED` in MySQL, `BIGINT` in MariaDB; `LAG`, `LEAD`, `FIRST_VALUE`, `LAST_VALUE` and `NTH_VALUE` widen the integers to `BIGINT` in MySQL and keep the type in MariaDB; `PERCENT_RANK` and `CUME_DIST` are not null in MySQL only.

A grouped block (`GROUP BY`, or an aggregate function in its select list, its `HAVING` or its `ORDER BY`) gives `Project(Sort(Window(Filter(Aggregate(...)))))`: the expressions above the aggregation read its columns, `#key1`, `#aggregate1`..., and those of the window functions, `#window1`...; a part equal to a key reads the key; a column neither grouped nor aggregated reads any value of its group, an implicit `ANY_VALUE` written as the column alone, which the MySQL family accepts when the column depends on the keys or without `ONLY_FULL_GROUP_BY` (the default of MariaDB), a setting of the server the transpiler leaves to the target. A `*` reads these columns too, a key or any value of its group for each column of the source, named as the source names them, which both dialects read alike (`crates/probe/cases/grouped-star.sql`). The emitter writes these columns back as what they stand for, and each key of `GROUP BY` in the form written.

Without grouping, `HAVING` filters the rows of the source after `WHERE` and before the window functions, `Window(Filter(Filter(source)))`, the filter of `HAVING` marked as such for the emitter. Each of its names reads the select list: the items of that name (an alias, a column, the name of an expression without alias), a single value when several have it (error 1052 otherwise), then an item that is that column of the source, under an alias too (`SELECT a AS x FROM t HAVING a > 1`). A name outside the select list reads an enclosing query, never the source (error 1054 without one): `(SELECT q.b FROM t AS q HAVING a > 1)` reads the `a` of the enclosing query. An alias reads its expression again (`RAND()` is computed once more). Both dialects read it alike, measured on each local image of MySQL, 8.0.11 to 9.3.0, and of MariaDB, 10.5.29 to 11.8.9 (`crates/probe/cases/having-alone.sql`).

From MariaDB, the `INT` of a literal is a `BIGINT` in MySQL: a value beyond it stops MariaDB under a strict mode (error 1264), is bounded to 2147483647 without, and MySQL keeps it **[decided autonomously]**;
- `cte.recursive-order`: towards MySQL, which reads the anchors first (error 3574), the anchors that MariaDB reads after a recursive part are written first, when one operator joins the parts and MariaDB reads their order as the standard does (`R UNION ALL A`, or after a first anchor no two anchors in a row); another order is refused;
- `cte.recursive-part`: towards MySQL, a read inside a derived table, `GROUP BY` and `DISTINCT` in a recursive part; towards MariaDB, a read on the inner side of an outer join. What both refuse goes through to the server: an aggregate, a window, a read inside a subquery or two reads in a part, `ORDER BY` over the parts;
- `cte.recursive-limit` (construct `recursive_limit`): `LIMIT` over the parts, read by MySQL from 8.0.19 (Bug #92857), refused before and by MariaDB;
- `cte.recursive-null`: a column of NULL in the anchors that a recursive part fills, an error in MySQL under a strict mode (1406), an empty string in MariaDB;
- the limit of the iterations goes through: a recursion longer than 1000 iterations fails in MySQL (`cte_max_recursion_depth`, error 3636), gives the rows of 1000 iterations in MariaDB (`max_recursive_iterations`), the variables of the session deciding **[decided autonomously]**;
- not supported yet: `CYCLE ... RESTRICT` of MariaDB, a read of an expression written after it in the same `WITH RECURSIVE` (another expression in MariaDB, a table in MySQL), a `WITH` inside a recursive expression, `EXCEPT` and `INTERSECT` between its parts, a first part that reads it without column list.

Then the items of the select list read through their alias inside an expression (`ORDER BY x + 0`, `GROUP BY x % 2`, `HAVING x > 1`; rules `alias.aggregate`, `alias.window` and `alias.having`; `emit/alias.rs`), measured on each local image of MySQL, 8.0.11 to 8.0.28, 8.0.30 to 8.0.35, 8.1.0 to 8.4.0, 8.4.11 and 9.3.0, and on each local image of MariaDB, 10.5.29 to 11.8.9 (`crates/probe/cases/alias-references.sql`). Both dialects read a name inside an expression of `ORDER BY` and `GROUP BY` as a column of the source first, then as an alias (`SELECT a AS b ... ORDER BY b + 0` sorts on the column `b`, `ORDER BY b` on the alias); `HAVING` reads a grouping column first, then an alias (`GROUP BY a % 2 HAVING b = 1` reads the alias `b`), and refuses the other columns of the source outside an aggregate function (error 1054); inside an aggregate function, the source first (`ORDER BY MAX(x)` reads the alias `x` when the source has no column `x`). An alias that two items have is ambiguous (error 1052). The plan keeps the item read through its alias (`ExprKind::Alias`: its name, and its expression, which the rules of the emitter reach), written by its name. Between dialects:

- `alias.aggregate` (construct `aggregate_alias_read`): towards MariaDB, which refuses an alias of an aggregate function inside an expression of `ORDER BY` or of a window (error 1247), and towards MySQL before 8.0.29, which reads it as one value for all the rows (section 6.3), the alias is written as its function (`ORDER BY s + 0` written `ORDER BY SUM(b) + 0`), computed over the same rows, of the same value when its arguments give the same value at each evaluation; an error otherwise (`SUM(b + RAND())`). From MySQL before 8.0.29, towards MariaDB and the later versions, an error: Prisme writes no emulation of a bug of the input **[decided autonomously]**;
- `alias.window` (construct `window_alias_once`): towards MySQL 8.0.16 to 8.0.28, which compute again a window function read through its alias inside an expression of `ORDER BY` (section 6.3), the alias is written as its function, over the same window, from MariaDB and from the other versions of MySQL; from these versions, towards an output that computes it once, an error; between 8.0.16 and 8.0.28, the alias goes through;
- `alias.having`: towards MariaDB, a name in `HAVING` of a grouping column and of an alias of an item other than an aggregate function or the column itself is an error: MySQL reads the column (warning 1052), MariaDB refuses the name as ambiguous (error 1052). A grouping key is written in `HAVING` as `GROUP BY` writes it: qualified (`GROUP BY t.b`), both read the column;
- a `JSON` that the dialects read otherwise is written as the expression of its item, for the rules of the `json` module;
- `HAVING SUM(s)`, an aggregate function of the alias of an aggregate function, is refused by Prisme, as by MySQL from 8.0.27 (error 1111), when MySQL before 8.0.27 and MariaDB read it **[decided autonomously]**: a rare form, whose value no manual describes;
- in a key of a window (`PARTITION BY`, `ORDER BY` of `OVER` and of the `WINDOW` clause, a window of `ORDER BY` included), a name alone designates an alias of the select list first in MariaDB, written after the window too, a column of the source only in MySQL; inside an expression, a column first, then an alias, in both; the arguments of a window function read no alias. The builder keeps the items written with an alias before it builds the windows, and builds the item where the window reads it **[decided autonomously]**. Towards MySQL, an alias read alone is written as its expression (`alias.window-name`), of the same value at each evaluation; towards MariaDB, and towards MySQL before 8.0.14 (construct `window_shadowed_column`), a column named alone that an alias of the select list other than this column names is written with its table (`alias.window-column`: `ORDER BY b` written `ORDER BY t.b`), an error when no single table of the source has it (a column of a join `USING`);
- in an `ORDER BY` after a `SELECT` between parentheses without `ORDER BY` or `LIMIT` of its own (rule `order.parenthesized`, `emit/parentheses.rs`; measured on 8.0.39 to 8.0.42, 8.4.2 to 8.4.5, 9.0.1, 9.1.0 and 9.2.0 too), MariaDB and MySQL read the names as those of an `ORDER BY` of the `SELECT` (`(SELECT a AS b FROM t) ORDER BY b + 0` sorts on the column `b`, `(SELECT id FROM t) ORDER BY a` on a column outside the select list), except MySQL 8.0.31 to 8.0.41, 8.1.0 to 8.4.4 and 9.0.0 to 9.2.0, which read the columns of the result (construct `parenthesized_order_result`, section 6.3); with an `ORDER BY` or a `LIMIT` between the parentheses, all read the columns of the result, except MariaDB before the fix of MDEV-29681 for a key other than a name alone or a position (construct `parenthesized_order_inner`), and every MariaDB for a subquery, sorted in no defined order: a derived table stands for the parentheses towards them, the query is refused from them **[decided autonomously]**. From the first ones, the builder reads that `ORDER BY` as the one of the block, written without parentheses, read alike everywhere. From the others, the plan sorts the result, written as is when each key reads the same values in the output, from a derived table otherwise (a name inside an expression that a column of the source has, other than the item itself; a subquery; a window function). From these versions, an expression of the alias of a grouping key that is an expression, in a block with aggregate functions, which they sort otherwise, is an error towards the others; a name of the column of an item other than its alias, which they read as well (`(SELECT a AS x ... GROUP BY a) ORDER BY -a`), is refused by Prisme (unknown column). MariaDB refuses these options too in a `SELECT` between parentheses followed by `ORDER BY` or `LIMIT` (`(SELECT HIGH_PRIORITY a FROM t LIMIT 2) LIMIT 1`, error 1234), which MySQL reads. MySQL has no `SQL_CACHE`, a name there (`SELECT SQL_CACHE a FROM t` reads the column `SQL_CACHE` under the alias `a`), and takes `SQL_NO_CACHE` anywhere, deprecated (warning 1681), several times.

- `option.dialect`: towards another dialect, the options without effect on the rows, all but `SQL_CALC_FOUND_ROWS`, are left out (point 42), `SQL_CACHE` towards MySQL, which has no query cache, among them; `SQL_CALC_FOUND_ROWS` sets what `FOUND_ROWS()` gives next, and goes through;
- `option.placement`: an option of the first `SELECT` only, on a `SELECT` that is another one in the output, inside the derived table that stands for parentheses towards MySQL before 8.0.31, or between parentheses followed by `ORDER BY` or `LIMIT` towards MariaDB: left out, without effect on the rows; an error for `SQL_CALC_FOUND_ROWS`;
- `option.found-rows` (construct `union_all_found_rows`): after `SQL_CALC_FOUND_ROWS` on a set operation of `UNION ALL` alone, with a `LIMIT` and without `ORDER BY`, `FOUND_ROWS()` counts every row in MySQL from 8.0.18, the rows up to the `LIMIT` before and in MariaDB (section 6.3): an error between them, the call of `FOUND_ROWS()` being in a next statement, out of reach of the transpiler.

Then the locking clauses, `FOR UPDATE`, `FOR SHARE`, `LOCK IN SHARE MODE`, `OF`, `NOWAIT`, `SKIP LOCKED` and `WAIT n` (rules `lock.share`, `lock.of`, `lock.clauses`, `lock.wait` and `lock.parenthesized`; `sql/parser/lock.rs`, `build/lock.rs`, `emit/lock.rs`, `locking.rs`), measured on each local image of MySQL, 8.0.11 to 9.3.0, and of MariaDB, 10.5.29 to 11.8.9 (`crates/probe/cases/locking.sql`, and `locking-scope.sql` for the rows locked; `docs/sources/mysql/locking-reads.md`, `docs/sources/mariadb/locking-reads.md`). MySQL reads `FOR UPDATE` and `FOR SHARE`, each one with `OF` and tables of the block, then `NOWAIT` or `SKIP LOCKED`, several clauses on distinct tables, and `LOCK IN SHARE MODE` alone; MariaDB reads one clause, `FOR UPDATE` or `LOCK IN SHARE MODE`, each one followed by `WAIT n`, `NOWAIT`, or `SKIP LOCKED` from 10.6.0 (MDEV-13115), without `FOR SHARE` nor `OF` (section 6.3). The plan keeps a `Lock` node above the block it locks, with its clauses and the tables they name (`plan/lock.rs`); a clause after a set operation locks its last operand, in both dialects. Between dialects:

- `lock.share`: `FOR SHARE` is written `LOCK IN SHARE MODE` towards MariaDB, which takes the same options; `LOCK IN SHARE MODE` followed by an option is written `FOR SHARE` towards MySQL, which reads it alone;
- `lock.of`: towards MariaDB, `OF` is left out when it names every table of the block, those of a common table expression and of a derived table read by the block aside; an error otherwise;
- `lock.clauses`: towards MariaDB, several clauses of the same lock and the same option, which together name every table of the block, are written as one; an error otherwise;
- `lock.wait`: towards MySQL, `WAIT 0` is written `NOWAIT`, which it is by the documentation of MariaDB; another timeout is an error, MySQL having no timeout of the locks for one statement (`SET_VAR` refuses `innodb_lock_wait_timeout`, error 3637); `SKIP LOCKED` towards MariaDB before 10.6.0, an error;
- `lock.parenthesized` (`locking` module): next to a query between parentheses, the rows a clause locks depend on the server (section 6.3). The builder refuses a clause that locks no row in the input, and names the place where it would lock them; the emitter writes the clause where the output locks the rows of the plan: after the outer clauses, at the end of the query between the parentheses, or in the derived table that stands for them **[decided autonomously]**. A `LIMIT` after the parentheses joins the locked block it bounds when that block has none (`(SELECT a FROM t ORDER BY a FOR UPDATE) LIMIT 1` written `SELECT a FROM t ORDER BY a LIMIT 1 FOR UPDATE`), which MySQL 8.0.19 to 8.0.25 read otherwise (construct `parenthesized_locked_limit`): from them, the query is refused **[decided autonomously]**;
- the default limit goes before the clause, at the end of the query between the parentheses when the clause ends it (`(SELECT a FROM t FOR UPDATE)` takes `(SELECT a FROM t LIMIT 1001 FOR UPDATE)`), which MySQL before 8.0.19 would drop before an outer `LIMIT` (`limit.rs`);
- not supported yet: a clause in a part of a recursive common table expression or after its parts; `INTO` and `PROCEDURE`, which are not read.

Both dialects read `@x`, its name made of the characters of a name, `.` and `$`, or quoted (`@'x'`, `@"x"`, `` @`x` ``), compared without case; `@` alone is the variable of an empty name, as `@''`, so that `@ a` is that variable, named `a` by its alias. They read `@@x`, `@@session.x`, `@@local.x` and `@@global.x`, the scope in any case and spaces around its dot, a reserved word after a dot only (`@@global.select`), the name between backticks (`` @@`x` ``), and before the name the instance of a structured variable or the component that defines the variable (`@@hot_cache.key_buffer_size`). They read `@x := value` as an operand whose value is a whole expression: `1 + @x := 2 * 3` gives 7, `@x := 0 OR 1` assigns 1, `- @x := 2` is `-(@x := 2)`; MySQL warns of an assignment outside `SET` from 8.0.13 (warning 1287, WL #12131). The plan keeps a `Variable` node, with its scope, the scope as written and the prefix of its name, and an `Assign` node. Decided autonomously, to be reviewed by the maintainer:

- the type of a user variable is read on the connection just before the query runs, with `SELECT @x, @y` (point 44; `Prepared::user_variables`, `catalog::user_variable_types`): the type of the start of the statement, the one the server reads even after an assignment of the same statement; the preview reads it on a new connection, where the variables are unset;
- an assignment gives its value as the variable keeps it: a boolean as an integer, a date or a time as text (`@x := DATE '2024-05-06'` is a `VARCHAR(10)` of the connection in MySQL, of `latin1` in MariaDB), a `JSON` as text, a hexadecimal or bit literal as bytes; it is written between parentheses inside another expression;
- a system variable is written as read, its value being that of the server of the output; its type is unknown to Prisme, and the translations that depend on the type refuse it (`CAST`, intervals, bit operations). Another variable absent from the output is refused by its server (error 1193), as `max_execution_time` of MySQL and `max_statement_time` of MariaDB: Prisme holds no list of the system variables of each version;
- `variable.renamed`: `tx_isolation` and `tx_read_only` of MariaDB, absent from MySQL (removed in 8.0.3, WL #9636), and `transaction_isolation` and `transaction_read_only` of MySQL, absent from MariaDB before 11.1.1 (MDEV-21921), are written by the name of the other dialect, of the same values (constructs `tx_variables` and `transaction_variables`);
- `variable.empty`: the variable of an empty name towards MariaDB from 10.7.1, which refuses it (construct `empty_user_variable`), its assignment towards MySQL, which refuses it (error 3061, construct `empty_user_variable_assignment`);
- a quoted name is written between backticks, which every SQL mode reads alike, the column keeping its name by an alias (`@'x'` is named `@'x'`);
- not supported yet: `SELECT ... INTO @x`, the parameters of a prepared statement (`?`); the statement `SET` belongs to step 8.

- `function.bit-count`: `BIT_COUNT` counts the bits of an integer, of a date or a time without a fraction of a second read as a number, of the index of an `ENUM` alike in both dialects. A byte string: MySQL counts the bits of its bytes, MariaDB reads it as a number; towards MariaDB, each hex digit of `HEX(x)` replaced by as many `x` as its bits, then `LENGTH`. A character string: MySQL reads an integer, its fraction dropped, MariaDB a decimal, rounded; from 2^63, MySQL bounds the integer to 2^63 - 1 or takes it as unsigned according to the expression (section 6.3). Towards MariaDB, a literal becomes `CAST(x AS SIGNED)`, which reads it as MySQL does, unless it starts with a line break or a vertical space, which MariaDB skips and MySQL does not (an error); another string is an error (decided autonomously: the reading of MySQL depends on the origin of a column, a table, a view or a derived table, which the emitter does not know, and on the version for a function). A number from 2^63: MySQL counts the bits of 2^63 - 1, MariaDB those of the number taken as unsigned, of 2^64 - 1 from 2^64; towards MariaDB, `LEAST(x, 9223372036854775807)`. Towards MySQL, a string or a large number is read as MariaDB does: `CAST(x AS DECIMAL(65, 30))` for a string, rounded, bounded to `[-2^63, 2^64 - 1]` by `LEAST` and `GREATEST`, then taken as the unsigned integer of the same bits by `(v + 2^64) % 2^64` cast to `UNSIGNED`, as `CAST` of a negative decimal to `UNSIGNED` gives 0 in MySQL 8.0.11 and wraps in 8.4; a string of more than 30 fractional digits is rounded at the 30th first. A floating point number is an error (decided autonomously: MySQL rounds half to even, MariaDB half away from zero, and `BIT_COUNT(9223372036854775808e0)` gives 63, 3 in MariaDB), as are a time with a fraction of a second (MySQL rounds the time to the second, the carry included, MariaDB the number it reads: `BIT_COUNT(TIME '10:00:59.5')` gives 6, 9 in MariaDB), a `JSON` and a type unknown. Checked on the servers, each emulation against the function of the input, MySQL 8.0.11 and 8.4 with MariaDB 10.6 and 11.8.
- `function.from-unixtime`: `FROM_UNIXTIME(n)` gives the date and time `n` seconds after the epoch within the range of `UNIX_TIMESTAMP` (below), NULL out of it, a `TIMESTAMP` in MariaDB from 11.7.1. Towards a wider range, `IF(n < cap, n, NULL)`; towards MariaDB from 11.7.1, the epoch rebuilt by `FROM_UNIXTIME(1) - INTERVAL 1 SECOND` and a `CAST` to the `DATETIME` of the fractional digits of `n` (0 for an integer, the scale of a decimal, 6 for a float or a string, measured; an error for a type unknown); towards MySQL from MariaDB 11.7.1, `NULLIF(n, 0)`. An integer of at most 4 bytes and a numeric literal bound `n`; beyond the range of the output, an error.
- `function.greatest`: `GREATEST` and `LEAST` compare numbers, strings, dates and times alike in both dialects, and a mix otherwise. A string with a number: as strings in MySQL, as `DOUBLE` in MariaDB; towards MariaDB, `CONCAT(n)` converts the numbers to strings, towards MySQL `s + 0e0` the strings to numbers. A date with a string: as dates, the result a string in MySQL, a date in MariaDB; towards MariaDB, `CONCAT(GREATEST(...))`, towards MySQL a `CAST` of the strings to `DATE`, or to the `DATETIME` of their fractional digits; each string a literal valid date, as MySQL leaves an invalid date out of the comparison where MariaDB takes it as a zero date or NULL. A time with a string or a number: as strings in MySQL, as times in MariaDB; towards MariaDB, `CONCAT` of the times and the numbers, towards MySQL a `CAST` of the strings to `TIME` (literal valid times; a number is an error). Integers or decimals with a `NULL` literal: their type in MySQL, a `DOUBLE` in MariaDB; towards MariaDB, the `NULL` becomes `IF(FALSE, x, NULL)`, `x` the first other argument, never evaluated; towards MySQL, `NULL + 0e0`. The context matters: MariaDB compares strings as numbers when the call is read as a number (`LEAST('10', '9') + 0` gives 9, 10 in MySQL), MySQL reads a date compared with a string as a number of the date, and compares a time with a string as numbers then. The emitter knows whether an expression is read as a value of its type: a column of the result of the statement, a key of `ORDER BY` or `GROUP BY` (`Emitter::column`); elsewhere, strings towards MariaDB are compared within `CONCAT(...)`, which reads the result as a string, and the other cases that depend on the context are errors (decided autonomously: the context of an operand is known only for these places for now). A `YEAR`, a `BIT`, a `JSON` and a type unknown, among which the result of a function, are errors. Checked on the servers, each emulation against the function of the input, MySQL 8.0.11 and 8.4 with MariaDB 10.6 and 11.8.
- `function.if`: `IF` reads its condition as `CASE WHEN` does; a `JSON` condition follows the rule `boolean.json` (step 5).
- `function.now`: `NOW`, `CURRENT_TIMESTAMP` and `SYSDATE` give a `TIMESTAMP` in MariaDB from 11.7.1, `LOCALTIME` a `TIME` from 11.6.2 (constructs `timestamp_now` and `time_localtime` of the reference file), a `DATETIME` in MySQL; towards those versions, `NOW`, `CURRENT_TIMESTAMP` and `LOCALTIME` become `LOCALTIMESTAMP`, the same instant of the statement, and `SYSDATE(n)` becomes `CAST(SYSDATE(n) AS DATETIME(n))` (decided autonomously: the cast makes the column nullable in the metadata, its values stay non-null); from MariaDB, `LOCALTIME` of those versions becomes `CURRENT_TIME`, and the `TIMESTAMP` of the others the `DATETIME` of MySQL, of the same value in the time zone of the session.
- `function.pad`: `LPAD` and `RPAD` without a pad pad with spaces in MariaDB, MySQL needs the pad (`' '` added). With an empty pad, beyond the length of the string, they give NULL in MariaDB and MySQL before 8.0.13, an empty string in MySQL from 8.0.13 and the string unchanged from 9.3.0 (constructs `pad_empty_string` and `pad_unchanged` of the reference file, read in the source of MySQL and measured on 8.0.11, 8.4 and 9.3.0); a literal pad other than the empty string goes through as is, another pad is an error when the two servers differ (decided autonomously: an emulation would evaluate the string, the length and the pad several times).
- `function.rounding`: `ABS`, `CEIL`, `CEILING`, `FLOOR`, `ROUND` and `TRUNCATE` read a date or a time as a number in MySQL, a `DOUBLE` (`CEIL(dt)` gives 20240506070810, `ROUND(TIME '10:20:30.5')` 102030, half to even), as a temporal value in MariaDB: `ABS` gives a `DECIMAL` of its digits, exact where the `DOUBLE` of MySQL rounds them (`ABS(TIMESTAMP '9999-12-31 23:59:59.999999')` gives 99991231235959.999999, 99991231235960 in MySQL), the others an integer for a `DATE` and a value of the type of the argument rounded otherwise (`CEIL(dt)` gives 2024-05-06 07:08:10, `ROUND(TIME '10:20:30.5')` 10:20:31, `ROUND(dt, -1)` keeps the seconds). Towards MariaDB, `x + 0e0`, of the same values, MySQL writing the `DOUBLE` with the digits of the fraction of the argument (`20240506070809.120` for `20240506070809.12`); towards MySQL, `x + 0` for a `DATE`, an integer, and `ABS(CAST(x AS DECIMAL(p, f)))` of its digits (8 for a date, 14 for a date and time, 7 for a time, and the digits of the fraction); a date and time or a time of the other functions, or an argument of a type unknown to Prisme, is an error (module `emit/rounding.rs`, measured on each local image, MySQL 8.0.11 to 9.3.0, MariaDB 10.5.29 to 11.8.9, `crates/probe/cases/rounding.txt`, `rounding-writes.txt`). The types of the results differ for the same values (`CEIL` of an `INT` is a `BIGINT` in MySQL, an `INT` in MariaDB, of a subquery of a `BIGINT` a `DECIMAL` in MySQL before 8.0.19, `ROUND(i, n)` of a column `n` a `DOUBLE` in MySQL before 8.0.22): no rule.
- `function.time-to-sec`: `TIME_TO_SEC` of a value that may have a fraction of seconds (a string, a decimal, a time with fractional digits) gives a whole number in MySQL, a decimal in MariaDB; towards MariaDB, `TIME_TO_SEC(x) DIV 1`; towards MySQL, an error (decided autonomously: an emulation of the fraction would not keep the scale of the result).
- `function.unix-timestamp`: `UNIX_TIMESTAMP(x)` gives the seconds from the epoch until 2038-01-19 03:14:07 UTC, 3001-01-18 23:59:59 in MySQL from 8.0.28, 2106-02-07 06:28:15 in MariaDB from 11.5.1, the epoch left out in MariaDB from 11.7.1 (constructs `unixtime_3001`, `unixtime_2106` and `unixtime_epoch_null`); out of the range, 0 in MySQL, NULL in MariaDB, and MySQL also gives 0 in the second after the epoch, its fraction dropped. Towards MariaDB, `IFNULL(u, 0)` (`u` the call written in the output), or a `CASE` that keeps `u` from 1 to the end of the range of MySQL and gives 0 otherwise to a non-null `x`; towards MySQL, a `CASE` that keeps the positive `u` within the range of MariaDB, gives 0 at the epoch, and computes the second after it as `UNIX_TIMESTAMP(x + INTERVAL 1 SECOND) - 1` (`TRUNCATE` to the digits of a literal string). A `TIMESTAMP` of the output and a valid literal date from 1971 to 2037 go through as written. Beyond the range of the output (MySQL from 8.0.28 towards MariaDB, MariaDB from 11.5.1 towards MySQL before 8.0.28), an error (decided autonomously: MariaDB computes no instant beyond 2106; an emulation by `TIMESTAMPDIFF` from its last second would be exact in a time zone of fixed offset and in the named zones, whose tables stop in 2037, never in the `SYSTEM` time zone of a system with daylight saving time). The argument that an emulation repeats must give the same value on each evaluation (neither subquery, nor stored or nondeterministic function), otherwise an error; the steps of a repeated expression are recorded once. Both rules checked on the servers, each emulation against the function of the input, at the bounds of the ranges, in UTC and at +05:00.
- `function.uuid`: `UUID()` gives a value of type `UUID` in MariaDB from 10.7.1 (construct `uuid_type`), of the same text as the `VARCHAR(36)` of MySQL but compared only with UUIDs; towards those versions, `CAST(UUID() AS CHAR(36))`; towards MySQL, the string of the same text.

Types of the results: each scalar function of a reference file carries the type of its result and its nullability in its dialect (keys `type` and `nulls`, module `function_types`), proposed from the calls generated by `probe calls` and measured on each local image (MySQL 8.0.11 to 9.3.0, MariaDB 10.5.29 to 11.8.9): 276 functions of MySQL and 341 of MariaDB have a type. A type of its own, the same whatever the arguments; a string of bytes after its arguments at some positions, of characters otherwise (a byte string as argument, hexadecimal literal, `CAST(s AS BINARY)`, `BIT` or geometry, or only `NULL`, measured by `crates/probe/cases/string-bytes.txt` and `string-kinds.txt`); or a type per period of versions (`PERIOD_ADD` an `INT` up to MySQL 8.0.23, a `BIGINT` from 8.0.24; `YEAR` a `YEAR` from 8.1.0; the predicates `MBR...` and `ST_...` a `BIGINT` up to 8.0.26, an `INT UNSIGNED` in 8.0.27, an `INT` from 8.0.28; `UUID()` a `UUID` in MariaDB from 10.7.1). Nullability: `NULL` only from an argument that may be (`nulls: args`, 104 functions of MySQL, 119 of MariaDB, with or without a type), never (`ISNULL`, `CHARSET`, `FIELD`...), or whatever the arguments. The plan types the calls from it: the rules read their results as those of a column of that type. The functions whose type depends on their arguments otherwise (`ROUND`, `COALESCE`, `ADDTIME`, `NULLIF`...) have no type yet and stay of a type unknown to Prisme, which the rules that need it refuse. A version from which a type changes is offered to the user, as those of the functions.

### Step 8. Catalog and session statements

Prisme translates them as far as needed (point 40). In the v1, between MySQL and MariaDB, and from PRQL; the other engines add their forms with their connector.

- **Relations of the catalog of Prisme**, with a fixed schema (databases, tables, columns, indexes, views, routines...), read by `Scan` nodes like tables. The introspection forms of each dialect map onto them: `SHOW TABLES`, `SHOW COLUMNS`, `DESCRIBE` and the `information_schema` views in MySQL and MariaDB; later `sqlite_schema` and the `PRAGMA` of SQLite, `pg_catalog` in PostgreSQL, the `duckdb_*()` functions of DuckDB.
- The emitter writes them with the means of the target, in the form that loses the least information and accepts the rest of the query (filters, joins, sorts): a query on `information_schema` in MySQL and MariaDB, or `SHOW` when the input used it and the target accepts it (origin, section 2.3; point 49).
- Example, once SQLite is an input dialect: `SELECT name FROM sqlite_schema WHERE type = 'table'` on a MySQL connection becomes a query on `information_schema.tables` (base tables of the current database). The columns MySQL cannot give in the same query (`rootpage`; `sql`, the text of creation, which MySQL gives table by table with `SHOW CREATE TABLE`) are listed in the report as a loss of precision.
- Session statements: `USE`, `SET` (session variables, `NAMES`, `TRANSACTION`) translated by meaning, towards the setting of the same meaning in the target, otherwise an explicit error. `EXPLAIN` of a DML query: the `EXPLAIN` of the target on the transpiled query; its output differs from one engine to another, which the report states.
- The other `SHOW` (`VARIABLES`, `STATUS`, `PROCESSLIST`, `GRANTS`, `WARNINGS`, `CREATE TABLE`...): one rule each, with its test.
- Report: a step kind "loss of precision", which says what the same request written in the dialect of the target would give in addition.
- **Tests**: on a test schema, the relations of the catalog give the same rows on MySQL and MariaDB; each rule has its test.

### Step 9. PRQL

- Lexer and parser of the whole language, chapter by chapter of the book: transforms (`from`, `select`, `derive`, `filter`, `sort`, `take`, `join`, `group`, `aggregate`, `window`, `loop`) and relation functions (`append`, `remove`, `intersect`), declarations (`let`, functions, modules), literals (dates `@2026-01-01`, ranges, f-strings, r-strings, s-strings), operators (`==`, `??`, `~=`, `//`, `**`...), `case`, the `prql` header, the standard library (`std`).
- Plan builder with the semantics of the book (`docs/QUESTIONS.md`, point 16), expressed by the explicit nodes of the plan: `== null` becomes a test of identity, `/` a division with a real result, `//` an integer division.
- Splitting of a PRQL text: PRQL has no separator character, a relation is delimited by its syntax (`let`, parentheses around a pipeline, braces of a tuple). The editor finds the declarations and the main query with the PRQL parser, never with the SQL splitter. Each relation is a query of the editor: Ctrl+Enter runs the relation under the cursor with the relations it depends on, Ctrl+Shift+Enter runs every relation, one result tab each (point 47).
- S-strings (raw SQL inside PRQL): read by the parser of the output dialect, explicit error if it does not understand them (point 45).
- `target` of the `prql` header: a target different from the engine of the connection is an explicit error (point 46).
- Editor: highlighting and completion of PRQL; the keywords route takes the input dialects.
- **Tests**: the examples of the book (their license is checked before copying them into the repository; otherwise examples written for Prisme), each compared with an equivalent SQL query: same plan, or same results on both servers.
- The PRQL choice appears in the profile and on the tab.

## 6. Feedback

Difficulties met, their solutions, and the particularities of the servers and versions found along the way, for the next implementations. Each entry says how it was established; the measures go through the tool `probe` (`docs/DEVELOPER.md`, section "Measurements on real servers").

### 6.1 Method

- **Measure, then read the source.** The manuals leave out the edge cases (empty pad of `LPAD`, first second after the epoch of `UNIX_TIMESTAMP`): `probe expr` measures them on several versions at once, the source of the server explains them and dates them (`LPAD` read in `sql/item_strfunc.cc` of MySQL 8.0.13 and in Bug #117227).
- **Bisect down to the patch versions of each branch.** A fix can come in a patch version of each branch maintained at the time, and in none of the others: the `XOR` of a fraction changed in MariaDB 10.11.19, 11.4.13 and 11.8.9, not in 10.6.28 nor in 11.0 to 11.3 and 11.7 (`crates/probe/cases/fraction-truth.txt`). A construct then has a period per branch.
- **Find the ticket of a change by its versions.** A change of behaviour may have no entry in the release notes. MariaDB: the tickets of a version, searched by words, through the API of its Jira (`/rest/api/2/search` with `fixVersion = "11.8.9" AND text ~ "hex"`), which gave MDEV-38061 for the hexadecimal literals. MySQL: the source of the two tags around the change (`sql/item.cc` of `mysql-8.0.26` and `mysql-8.0.27` on GitHub), which gave `Item_hex_string::val_int`.
- **Run the cases on every local image.** `probe --all` takes each local image of MySQL and MariaDB, one per version of server, read from the environment of the image (`MYSQL_VERSION`, `MARIADB_VERSION`: `mariadb:11.8` is 11.8.9), and starts them by groups of 5 (`--group`), each group stopped before the next: 53 servers run 8 statements in 2 min 33 s. Started all at once, 23 servers no longer answered within 300 s. The results come per version (`--layout rows` for `expr`), and the thresholds are read from them, without bisecting round after round.
- **Run the conformance suite on both sides of each threshold.** The cases of a construct cover the forms thought of: run with `PRISME_CONFORMANCE_SERVERS` on the versions around each threshold, the suite found that MySQL 8.0.18 sorts a union between parentheses by the outer `ORDER BY` before its own `LIMIT`, a form missing from `crates/probe/cases/parenthesized-limits.sql`, added since.
- **Bracket a change between two images.** The images are published per patch version (`mysql:8.0.27`, `mysql:8.0.28`): the version of a change is measured on both sides. Some versions have no image (MariaDB 11.7.0 and 11.7.1, the first 11.7 image being 11.7.2): the `since` then comes from the fix version of the ticket, confirmed on the neighbouring images.
- **Measure up to the last version of each branch.** A change can be undone later, without a release note: the names of an `ORDER BY` after a `SELECT` between parentheses, read as the columns of the result from 8.0.31, are read as before again from 8.0.42, 8.4.5 and 9.3.0 (section 6.3). The newest images showed it, grouped with 8.0.30; the images in between, pulled for it, bracketed it.
- **Give the rows of a case values that differ.** Two groups of the same sum (30 and 30) made `ORDER BY s + 0` right on every version of MySQL, and the conformance suite passed; with counts of 1 and 2, MySQL before 8.0.29 sorts nothing (section 6.3). A sort, a rank or a partition is measured on values that each order tells apart.
- **Measure each arrangement of the parts of a construct.** MariaDB reads `R UNION ALL A`, a recursive part before an anchor, as the standard does, but keeps the last of two anchors in a row after a recursive part (`R UNION ALL A1 UNION ALL A2` gives the rows of `A2` alone), which the case of two parts did not show: the conformance suite found it on the reordering towards MySQL (`crates/probe/cases/with-recursive.sql`).
- **Check each emulation on columns, literals and functions.** A server reads a literal, a column and the result of a function differently, and folds the constants: an emulation right for `'18446744073709551615'` was wrong for a column holding it (`BIT_COUNT`, section 6.3).
- **Check each emulation against the function of the input.** A unit test only checks the text written. The emulation is run on the output server and the function on the input server, value by value, at the bounds of the ranges and beyond, in UTC and in another time zone (+05:00). This check found the first second after the epoch of `UNIX_TIMESTAMP` and the scale given by `x + INTERVAL 1 SECOND`, which the unit tests could not see. The conformance suite (section 4) keeps it, on tables, for each new version.
- **Compare the values, then the types.** The same function gives decimals of other precisions on the two servers (`UNIX_TIMESTAMP('…00.5')`: `DECIMAL(12,1)` in MySQL, `DECIMAL(17,1)` in MariaDB). The scale is kept by the emulations; the precision waits for the result types of the functions.
- **Read a type through `CREATE TABLE ... AS SELECT`**, the value from the column created. A user variable converts some values (a binary string read as `0x0` in MySQL 8.4). MariaDB 10.6 refuses the `CREATE TABLE ... AS SELECT` of a `JSON` column (error 1054, "Unknown column in CHECK"): `probe` then reports the type as unknown.
- **Classify the names of functions by the error of a call**, made inside `SELECT 0 + ...` so that the select modifiers (`ALL`, `DISTINCT`, `STRAIGHT_JOIN`, `SQL_*_RESULT`) are not taken for functions: 1305, no function of that name; 1582, another number of arguments; 1064, syntax of its own; 1630, a stored function named like a built-in one, which is also the error of a quoted built-in name (`` `NOW`() ``). The spatial constructors of MariaDB (`POINT`...) answer only with their exact number of arguments: a name is built-in when any form of the call reaches the function.
- **Read the results of the generated calls by a few principles** (decided autonomously, to be reviewed by the maintainer). The calls of `probe calls` give, for each function, its results on each version of both servers; a difference calls for a rule only when it changes what the translated query gives. Every error counts as one result, whatever its code. An error of the input with a value of the output is accepted: the translated query does more than the input. A value of the input with an error of the output is explicit, the server refusing the query; Prisme refuses it before when it can tell from the plan. Two values that differ call for an emulation or a refusal. Two floating point numbers that differ in their last digits are taken as alike (`LOG2(1e1)` gives 3.321928094887362 in MySQL, 3.3219280948873626 in MariaDB: MySQL computes `log2`, MariaDB `log(x) / M_LN2`). A difference that comes from a setting of the server follows the target, the query being run there: the collation of the connection, `max_allowed_packet` for `REPEAT` and `SPACE`, the text of `VERSION()` and `SESSION_USER()`. Two types of the same values may be accepted, as the `YEAR` that `YEAR(d)` gives from MySQL 8.1.0, an `INT` before.

- **Measure the precedence of a construct against each operator around it**, on both sides and in both dialects: `x + INTERVAL n unit` closes at its unit, then takes `*` and `^` on the sum, which no table of precedence of the manuals says (`crates/probe/cases/interval-precedence.txt`). The parser reads the interval at the level of `+`, then continues the loops of the higher levels from the sum (`binary_level_from` in `sql/parser/expr.rs`).
- **Check a reader of strings against a table of measures.** The strings of the typed literals are read by Prisme as each server reads them: 292 strings measured on four servers fill a table (`temporal/tests.rs`), each value compared with the reading of Prisme, each string Prisme leaves to the server marked `?`. Measuring the strings by families (separators, digits, letters, bounds) found the forms one dialect reads only.
- **Measure a rounding where it carries.** `BIT_COUNT` of a time with a fraction gave the same values on `10:00:00.6`; at `10:00:59.5`, MySQL rounds the time and carries into the minute (100100), MariaDB rounds the number (100060), and the rule had taken them as alike (`crates/probe/cases/bit-count.txt`). Each rounding is measured at the carry: 59.5 seconds, `23:59:59.5` of the last day of a year, a half at the last digit.
- **Find where a default comes from.** A default can come from the configuration of the packages: the image of MariaDB 11.4.13 gives `_utf8mb4'a'` the collation `utf8mb4_uca1400_ai_ci` because its `50-server.cnf` sets `character-set-collations = utf8mb4=uca1400_ai_ci`, the server itself changing its default in 11.5.1 only (MDEV-25829). `SELECT @@character_set_collations` on each image, then `mariadbd --no-defaults --verbose --help` in the container, tell the two apart (`crates/probe/cases/charset-variables.sql`).
- **Measure the locks inside a transaction, after a pause.** The rows a statement locks are read in `information_schema.INNODB_TRX` (`trx_rows_locked`, `trx_tables_locked`) before the `ROLLBACK`: the view is cached for 0.1 s, a `DO SLEEP(0.15)` before reading it gives the count of the statement, without it the count of the previous one. A table of 5 rows gives 6 for a full scan, the supremum record included. A count of 0 can also come from the rows read in streaming, the server stopping before it reads the locked table: a case that locks nothing is checked against the same query without clause.
- **Measure an aggregate function as a window function apart.** The servers compute a window with other code than the aggregate: MariaDB reads its values alike, but computes `BIT_XOR` from bit 31 and the frames that remove rows wrong (MDEV-35439, MDEV-40689). A case per kind of frame (the whole partition, a running frame, a frame whose start moves) and per range of values (below 2^31, from 2^31, NULL) finds them; the tickets of the server, searched by the name of the function, confirm them.
- **Set the value a construct reads.** `SELECT @ a` gave NULL in a column named `a`, as the variable `a` unset would; with `SET @a = 7` first, it still gave NULL: `@` alone is the variable of an empty name, and `a` its alias (`crates/probe/cases/variables-grammar.sql`). A case that only reads NULL tells no construct from another.
- **Compare two forms over all the code points.** A class of a pattern covers thousands of characters, which a few subjects do not cover: `crates/probe/cases/regexp-classes.sql` matches each form, written for each library, against every code point of planes 0 to 3 and 14 that all the servers measured assign (134,637), and gives the count and a hash of the code points matched; a difference is then listed code point by code point (U+180E for `\s`, U+0345 for `\p{L}` under case insensitivity). The single characters under case insensitivity were compared so as well, each cased character, alone and in a class, against the 2,927 cased code points.

### 6.2 Emitter

- **The rules of the reference files apply between dialects only.** Between two versions of a dialect, a function goes through as written, even when its behaviour changed (`UNIX_TIMESTAMP` from MySQL 8.0.19 to MySQL 8.4); a rule written for both directions only meets the pairs MySQL → MariaDB and MariaDB → MySQL.
- **An emulation that repeats an argument** (`CASE WHEN UNIX_TIMESTAMP(x) < ... THEN UNIX_TIMESTAMP(x) ...`) needs an argument that gives the same value on each evaluation: neither subquery, nor stored function, nor function of `VOLATILE` (`emit/rules.rs`, `repeatable`); otherwise an error. The steps of the repeated argument are recorded once.
- **The types of the results of functions are unknown in the plan** for now, those of the current date and time aside (`NOW()`, `CURDATE()`...), and those of the functions of JSON of MySQL that give a `JSON`: `IFNULL(dt, s)` is nullable, of a type unknown. A rule that depends on the type takes the form that is right for any value (`UNIX_TIMESTAMP` of such a call keeps the test of the fraction), or gives an error when it cannot (the fractional digits of the cast of `FROM_UNIXTIME`, an interval or `TIMESTAMPDIFF` of such a call).
- **`NULLIF` evaluates its first argument twice** when it differs from the second, on both servers (`SET @c = 0` then `NULLIF((@c := @c + 1), 0)` gives 2, measured on MySQL 8.0.11 and 8.4, MariaDB 10.6 and 11.8): an emulation that writes it repeats its argument.
- **A rule can apply between two versions of a dialect.** `interval.time` compares the readings of the input and of the output, versions included: a `TIME` moved by days is a `DATETIME` in MySQL from 8.0.28, a `TIME` before, so the rule meets MySQL 8.4 → MySQL 8.0.27 as well as MySQL → MariaDB. A rule of a construct of the versions reads `Emitter::input_has` and `Emitter::has`.
- **Avoid `LEAST` and `GREATEST` to bound an argument** in an emulation: their comparison of a string with a number differs between the servers (section 6.3).
- **The value of a call can depend on the expression that reads it.** A server asks an expression for a string, a number or a date depending on its parent, and some functions compute differently for each: `LEAST('10', '9')` gives `'10'`, `LEAST('10', '9') + 0` gives 9 in MariaDB (10 in MySQL), as does `ABS(...)`, `SUM(...)`, or a scalar subquery read as a number. Measure each rule inside `+ 0`, `CONCAT(...)` and `CAST(... AS SIGNED)` as well as alone. `Emitter::column` tells a rule whether its call is read as a value of its type, `Emitter::number` whether it is read as a number (an operand of an operator other than `LIKE`, an argument of an aggregate or window function that reads numbers); a string function around the call (`CONCAT(x)`) makes the server read it as a string whatever its parent.
- **`CONCAT(x)` converts a number to a string that gives way to the collation of a column**, as the implicit conversion of MySQL does; `CAST(x AS CHAR)` takes the coercibility of a column in MySQL and MariaDB 10.6, that of a literal in MariaDB 11.8 (`COERCIBILITY()` measured).
- **A rule meets the types of the catalog of the target.** The plan takes the column types from the server that runs the query: a `JSON` column of MariaDB read as a `LONGTEXT` left the rules `boolean.json` and `json.text` silent from MySQL, and hid a gap of `json.text` (`COUNT(j) OVER ()` refused once the type was read). A type added to the catalog is checked in both directions, by the conformance suite.
- **Write a conversion at the value, once.** A `JSON` read as its text is written `CONCAT(j)` around the column, its readers (`MIN`, `COALESCE`, `=`) taking the text from it; written around each reader, it would give `CONCAT(MIN(CONCAT(j)))`. A flag of the emitter (`json_as_is`), set by the readers that take the value as is, lists those in one place; every other reader gets the text.
- **An item read through its alias stays a node of the plan**, its expression inside (`ExprKind::Alias`). The rules that rewrite expressions reach the expression, the emitter writes the name: replaced by its expression in the plan, `HAVING x = 1` was written `HAVING a % 2 = 1` by the regrouping of the keys, a name of the input lost and its computation repeated. The regrouping enters the node without replacing it.
- **`HAVING` of MySQL names the columns of `GROUP BY`, not those of its expressions**: `GROUP BY CONCAT(j) HAVING CONCAT(j) < '2'` is error 1054, unknown column `j`, in MySQL 8.0.11 and 8.4.11 as in MariaDB 10.6.28 and 11.8.9; `HAVING CONCAT(ANY_VALUE(j))` too in MySQL. A key added as is after the key it depends on (`GROUP BY CONCAT(j), j`) groups alike and makes `j` a column of `GROUP BY`; with `WITH ROLLUP`, it would add a level of totals.
- **Prisme leaves the session time zone at the default of the server.** The tables of the named time zones stop in 2037 (the last offset applies beyond), the `SYSTEM` time zone follows the rules of the system, daylight saving time included: no emulation computes an instant beyond the range of MariaDB (2106) exactly in every time zone.
- **Tell the case of a collation inside a pattern.** With a collation of unknown case, an alternative that only case insensitivity matches carries a lookahead that requires two characters of different cases at once: `(?=S)s` matches `s`, `S` and `ſ` under case insensitivity, nothing otherwise; `(?<=E)` after a literal `e` does the same for the character before (`crates/probe/cases/regexp-syntax.txt`). An emulation then stays one pattern, whatever the collation of the column.
- **A quantifier applies to the last atom.** An emulation of a class by a lookahead and a class (`(?![_])[...]`) lost its quantifier to the class alone: `[^\W_]+` matched `word_1` towards PCRE2. A rewritten token that a quantifier can follow is a single atom, a class or a group; the conformance suite found it, where the unit tests compared the text written.
- **A text of the input written as is carries its comments.** A literal of several tokens written from the input (`'a' /* x */ 'b'`, `DATE /* y */ '2024-05-06'`, `_latin1 /* z */ 'c'`) holds its comments, which the emitter wrote again before the next item: the comments inside such a text are passed once it is written (`Emitter::input_text`).

### 6.3 Particularities of the servers and versions

- **Range of `UNIX_TIMESTAMP` and `FROM_UNIXTIME`**: until 2038-01-19 03:14:07 UTC before MySQL 8.0.28 and MariaDB 11.5.1, 3001-01-18 23:59:59.999999 in MySQL from 8.0.28 (on 64-bit platforms), 2106-02-07 06:28:15 in MariaDB from 11.5.1, the epoch left out in MariaDB from 11.7.1. Out of it, `UNIX_TIMESTAMP` gives 0 in MySQL (with a warning for a zero date), NULL in MariaDB, and `FROM_UNIXTIME` NULL on both (MariaDB adds the warning "Truncated incorrect unixtime value").
- **First second after the epoch**: MySQL gives 0 with the scale of the argument (`UNIX_TIMESTAMP('1970-01-01 00:00:00.5')` gives `0.0` in UTC), MariaDB the fraction (`0.5`).
- **Zero dates**: `UNIX_TIMESTAMP` of a zero `TIMESTAMP` column gives 0 on every server; of a zero `DATETIME` or string, 0 in MySQL, NULL in MariaDB.
- **MariaDB 11.7.1** (MDEV-15751): `NOW()`, `CURRENT_TIMESTAMP`, `SYSDATE()` and `FROM_UNIXTIME()` give a `TIMESTAMP`; `FROM_UNIXTIME(0)` gives NULL, `FROM_UNIXTIME(1) - INTERVAL 1 SECOND` the epoch as a `DATETIME`; `IF(c, <DATETIME>, <TIMESTAMP>)` gives a `DATETIME`. **MariaDB 11.6.2**: `LOCALTIME` gives a `TIME`. **MariaDB 10.7.1**: `UUID()` gives a `UUID`.
- **Fractional digits of `FROM_UNIXTIME(n)`**, the same on both servers: 0 for an integer, a boolean, NULL, a date or a time without fraction; the scale of a decimal, 6 at most; those of a `DATETIME(n)` or `TIME(n)`; 6 for a float or a string. `x + INTERVAL 1 SECOND` gives 6 fractional digits to a string `x`.
- **Fractional seconds of `CAST`**: MySQL rounds them, MariaDB truncates them (`CAST('1970-01-01 00:00:00.5' AS DATETIME)` gives `00:00:01` in MySQL, `00:00:00` in MariaDB), under the default SQL modes (`TIME_TRUNCATE_FRACTIONAL` of MySQL and `TIME_ROUND_FRACTIONAL` of MariaDB reverse them): a `DATETIME`, a `TIMESTAMP` or a `TIME` to an integer or to fewer fractional digits, a decimal, a float or a string to a `DATETIME` or a `TIME`. To `DATE`, both drop the time.
- **`LPAD` and `RPAD` with an empty pad**, beyond the length of the string: NULL in MariaDB and in MySQL before 8.0.13, an empty string from 8.0.13, the string unchanged from 9.3.0. MariaDB pads with spaces without a third argument, MySQL refuses it (error 1582).
- **`TIME_TO_SEC`** of a value with a fraction: a whole number in MySQL, a decimal in MariaDB.
- **Binary arguments of the string functions in MySQL**: `REPLACE`, `SUBSTRING_INDEX` and `TRIM` take the character set of their string from 8.0.19 (Bug #30114420), a binary argument converted to it at execution, error 3854 for bytes invalid in it (`REPLACE('ab', X'FF', '-')`); `LOCATE`, `INSTR` and `POSITION` search in the collation of their string from 8.0.26, without entry in the release notes (`Item_func_locate::resolve_type` of the source), and ignore a `COLLATE` of the substring (`POSITION('B' COLLATE utf8mb4_bin IN 'abc')` gives 2, 0 before and in MariaDB). Measured on 8.0.12 to 8.0.26, 8.4.11, MariaDB 10.6.28 and 11.8.9 (`crates/probe/cases/string-binary.txt`). With three arguments, `LOCATE` counts its start in characters of the string, then, for a binary substring before 8.0.26 and in MariaDB, the bytes up to the substring.
- **`BIT_COUNT`** of a byte string counts the bits of its bytes in MySQL (a feature of the bit operations on byte strings of MySQL 8.0), reads it as a number in MariaDB; of a character string, MySQL reads an integer, its fraction dropped (as `CAST(x AS SIGNED)`), MariaDB a decimal, rounded (as `CAST(x AS DECIMAL(65, 30))`). Its result is a `BIGINT` in MySQL, an `INT` in MariaDB.
- **Bit operators of byte strings in MySQL** (`crates/probe/cases/bitwise-binary.sql`): computed byte by byte when every operand is a byte string (a `VARBINARY` or `BINARY` column, `_binary`, `CAST(x AS BINARY)`, `CONCAT` of byte strings), the left one of a shift and the only one of `~`; a hexadecimal literal counts as a byte string with another one, two hexadecimal literals are read as numbers. A `BIT`, an integer, a character string or NULL with a byte string gives a numeric evaluation. The result is a `VARBINARY`, and error 3513 refuses byte strings of different lengths. MariaDB always reads numbers.
- **Operands of the bit operators** (`crates/probe/cases/bitwise-readings.sql`, `bitwise-numbers.txt`): read as `BIT_COUNT` reads its argument, on every server and for every expression; `-1e20 | 0` is an error 1690 in MySQL 8.4.11, bounded elsewhere. `BIT_AND`, `BIT_OR` and `BIT_XOR` read a string, a decimal and a floating point number as the operators of MySQL in both dialects, which differs from the operators of MariaDB (`BIT_OR('3.7')` gives 3, `'3.7' | 0` 4 in MariaDB; `crates/probe/cases/bitwise-aggregates.sql`).
- **A time with a fraction read as an integer** (`crates/probe/cases/bit-count.txt`, `bitwise-numbers.txt`, `bitwise-aggregates.sql`): the bit operators and `BIT_COUNT` of MySQL round the time to the second, the carry included (`TIMESTAMP '1999-12-31 23:59:59.6' | 0` gives 20000101000000), those of MariaDB round the number (19991231235960); `BIT_AND`, `BIT_OR` and `BIT_XOR` of MySQL round the time, those of MariaDB truncate it. The other readings of a time as an integer (`DIV`, `CAST(x AS SIGNED)`) remain to be measured.
- **Count of a shift** (`crates/probe/cases/bitwise-shifts.txt`): read alike, then MySQL shifts out every bit from 64, MariaDB takes the count modulo 2^32 (`1 << 4294967297` gives 0, 2 in MariaDB; `1 << -9223372036854775808` gives 0, 1 in MariaDB). MySQL stops at a line break before a string count (`1 << '\n3'` gives 1, 8 in MariaDB).
- **`BIT_AND`, `BIT_OR` and `BIT_XOR` as window functions** (`crates/probe/cases/bitwise-windows.sql`): from MySQL 8.0.12 (WL#11573, error 1235 in 8.0.11). MariaDB 10.6.28 and 11.8.9 read their values as the aggregate functions, but set the bits from 31 of `BIT_XOR` wrong, whatever the frame (MDEV-35439: `BIT_XOR` of 3 then 2147483648 over a running frame gives 18446744071562067971), and lose count of the NULL values of a frame whose start moves (MDEV-40689, fixed in 11.4.14 and 11.8.10: `BIT_AND` over `ROWS BETWEEN 1 PRECEDING AND CURRENT ROW` gives 18446744073709551615 after a NULL).
- **`AES_ENCRYPT`, `AES_DECRYPT`**: their fourth argument is a key derivation in MySQL (from 8.0.30), a mode in MariaDB (from 11.2.1, with the vector and the variable `block_encryption_mode`, MDEV-9069). MySQL 8.4 warns of a key that is not 16 bytes long, MariaDB does not; the width of the type of `AES_DECRYPT` of a constant differs (`VARBINARY(7)` in MySQL, `VARBINARY(28)` in MariaDB for 7 bytes).
- **A string read as an integer in MySQL** (`BIT_COUNT(s)`, measured on 8.0.11, 8.0.17, 8.0.22, 8.0.28, 8.4.11 and 9.3.0, against MariaDB 10.6.28 and 11.8.9): its integer part, without exponent (`'1e19'` gives 1), bounded to 2^63 - 1 or taken as unsigned from 2^63 according to the expression. A column of a table, `IF` and `CASE` bound it, after all the spaces (line breaks and vertical spaces included); a literal, a user variable, `COALESCE` and `IFNULL` take it as unsigned, after spaces and tabs only; a string function (`CONCAT`, `LOWER`, `CAST(x AS CHAR)`...) bounds it up to 8.0.28 at least and takes it as unsigned from 8.4; a column of a view, of a derived table or of a common table expression reads as the expression it stands for, when the server merges it into the query (a `UNION` is not merged, and bounds). `CAST(x AS SIGNED)` of MariaDB reads the integer part after all the spaces and takes it as unsigned from 2^63 (`'18446744073709551615'` gives -1), for a literal as for a column; MariaDB reads a string as a number with its exponent elsewhere (`BIT_COUNT('1e19')` gives 19 bits).
- **Type of an integer literal** (`crates/probe/cases/integer-literals.txt`, measured on each local image of MariaDB, 10.5.29 to 11.8.9): MariaDB gives an `INT` to a literal of at most 9 characters, leading zeros and a minus included, a `BIGINT` beyond, whatever its value (`999999999`, `000000001` and `-99999999` are `INT`s, `1000000000`, `0999999999` and `-999999999` `BIGINT`s); MySQL gives a `BIGINT` to every integer literal. A column that stores the literal takes its type (a table created from a query, a recursive common table expression).
- **Recursive common table expressions** (`crates/probe/cases/with-recursive.sql`, measured on each local image, MySQL 8.0.11 to 9.3.0, MariaDB 10.6.28 to 11.8.9): the columns take the type of the anchors, nullable, in both. MySQL reads the anchors before the recursive parts (error 3574); MariaDB reads them in any order (measured on 10.6.28, 10.11.19, 11.4.13 and 11.8.9), but keeps the last of two anchors in a row after a recursive part (`SELECT 1 UNION ALL R UNION ALL SELECT 10 UNION ALL SELECT 20` drops 10), and refuses two recursive parts after a first one (error 1235, "mix of ALL and DISTINCT", every operator being `UNION ALL`). MySQL refuses a read inside a derived table (3577), `GROUP BY` (3575) and `DISTINCT` (1235) in a recursive part, which MariaDB reads, giving rows the standard does not (`SELECT n + 1 FROM r WHERE n < 3 GROUP BY n` repeats 2 up to the limit of the iterations). MariaDB refuses a read on the inner side of an outer join (4008) and `LIMIT` over the parts (1235), which MySQL reads from 8.0.19. A column of NULL in the anchors is a `BINARY(0)`: another value is the error 1406 in MySQL under a strict mode, an empty string in MariaDB and in MySQL without strict mode.
- **Limit of the iterations of a recursive expression**: MySQL fails beyond `cte_max_recursion_depth` iterations (1000, error 3636, "aborted after 1001 iterations"), whatever the outer `LIMIT`; MariaDB stops after `max_recursive_iterations` (1000 from 10.6.0, MDEV-17239, 4294967295 before) and gives the rows found, with the warning 1931 from 10.6.15, 10.9.8, 10.10.6, 10.11.5, 11.0.3 and 11.1.2 (MDEV-31214), without before (measured on 10.7.8, 10.8.8, 10.11.2 and 11.0.2).
- **Type of `CASE` over integers**: MySQL gives an `INT`, a `BIGINT` or a `DECIMAL(20, 0)`, MariaDB keeps the size of the largest integer; an unsigned integer with a signed one gives a `DECIMAL` in MariaDB (`CASE WHEN c THEN iu ELSE i END` is a `DECIMAL(10, 0)`, an `INT` in MySQL, the value 4294967295 included), and so does an unsigned integer with a `NULL` literal, as in `IFNULL`, `COALESCE` and `UNION` (`CASE WHEN c THEN bu ELSE NULL END` is a `DECIMAL(20, 0)`, a `BIGINT UNSIGNED` in MySQL). `IF`, `NULLIF`, a `CASE` without `ELSE` and `CAST(NULL AS UNSIGNED)` keep the unsigned integer in MariaDB. In a `CREATE TABLE ... AS SELECT`, MySQL 8.0.11 and 8.4.11 type `CASE WHEN c THEN 4294967295 ELSE NULL END` as an `INT` and refuse its value (error 1264).
- **Scale of a `DECIMAL` `CASE` in MySQL**: written as a string, each value has the scale of its result (`CASE WHEN c THEN 42 ELSE 12.50 END` gives `42` and `12.50`, `CONCAT` and `LIKE` read `'42'`), as does `IF`; `IFNULL`, `COALESCE`, `GREATEST`, arithmetic, aggregate and window functions give the scale of the type, as do a temporary table (`GROUP BY`, `DISTINCT`, `UNION`, a materialized derived table) and a scalar subquery in 8.0.11 (not in 8.4.11). MariaDB gives the scale of the type everywhere.
- **`CAST` of a negative decimal to `UNSIGNED`** gives 0 in MySQL before 8.0.19 and in MariaDB, the integer of the same bits in MySQL from 8.0.19 (`CAST(-3.7 AS UNSIGNED)`, measured on 8.0.18 and 8.0.19); of a negative integer, the integer of the same bits everywhere. Of a negative float or time, the integer of the same bits in MySQL, 0 in MariaDB; of a float from 2^63, 9223372036854775807 in MySQL, the integer in MariaDB (`1e300` gives 18446744073709551615).
- **`CAST` of a value that is not a date to a date or a time** (a number, bytes, an `ENUM`, a `SET`, a `BIT`, a `YEAR`): NULL with a warning in MySQL, a zero date in MariaDB; a time out of range, NULL in MySQL, its bound in MariaDB (`838:59:59`, `838:59:59.9` for a `TIME(1)`); a `YEAR` to `TIME`, `00:20:24` in MySQL, `00:00:00` in MariaDB.
- **`CAST` of a string to a date**: MySQL converts a time zone offset to UTC from 8.0.19 (`'2024-05-06 23:00:00+02:00'` gives `21:00:00`), MariaDB ignores it. Under their default SQL modes, MySQL gives NULL to a zero date (`NO_ZERO_DATE`), and from 8.0.24 to a zero day or month (`NO_ZERO_IN_DATE`, ignored by `CAST` before), MariaDB keeps them; `'900:00:00'` gives `0900-00-00` in MariaDB and in MySQL before 8.0.28, NULL from 8.0.28. `'2024-05-06'` to `TIME` gives `00:20:24` on every server.
- **`CAST` of a string to an integer**: MySQL stops at a line break, a vertical tab, a form feed or a carriage return before the number (`CAST('\n12' AS SIGNED)` gives 0), MariaDB skips them (12); both skip spaces and tabs. A hexadecimal literal reads as a number in MySQL (`CAST(X'41' AS SIGNED)` gives 65), as a string in MariaDB (0); a `VARBINARY` column as a string in both.
- **`CAST` to `FLOAT` beyond 3.4e38**: error 1690 in MySQL, the largest `FLOAT` in MariaDB. A float literal beyond the integers to `SIGNED` (`-1e19`): error 1690 in MySQL 8.4, bounded in MariaDB and for a column.
- **`CAST` of bytes to characters**: an invalid sequence gives its bytes in MySQL until 8.0.27, NULL from 8.0.28 under a strict mode (an empty string otherwise), `?` in MariaDB.
- **Typed literals of more than 6 fractional digits**: MySQL rounds them on the seventh digit, with its carry (`TIME '07:08:59.9999995'` gives `07:09:00.000000`, `TIMESTAMP '2024-12-31 23:59:59.9999995'` gives `2025-01-01 00:00:00.000000`), an error beyond `9999-12-31` (1441) or `838:59:59` (1525), or for a zero date carried to the next day; MariaDB truncates them, under its default SQL mode (`TIME_ROUND_FRACTIONAL` rounds them, a mode MySQL refuses; the `TIME_TRUNCATE_FRACTIONAL` of MySQL leaves the literals rounded). A `TIME` of 10 digits or more: MySQL truncates some (`.1234567890` gives `.123456`) and rounds others (`.9999999999` gives `07:08:10`).
- **`TIME` moved by days or longer** (`t + INTERVAL 1 DAY`, `DATE_ADD`, `TIMESTAMPADD`): a `DATETIME` in MySQL from 8.0.28, the time read on the current date (`TIME '-01:00:00' + INTERVAL 1 DAY` gives today at 23:00:00, Bug #103781); before 8.0.28, a `TIME` of the hours added by `DAY`, `WEEK` and the compound units of `DAY`, NULL of type `TIME` by `MONTH`, `QUARTER`, `YEAR` and `YEAR_MONTH`; in MariaDB, a `TIME` by `DAY` and its compound units, NULL of type `DATETIME` by `WEEK` and longer (warning "time field overflow"). Bisected on the images 8.0.20 to 8.0.28.
- **Date and time arithmetic of a string or a number**: a `VARCHAR` of 29 characters in MySQL, of the date, the time and their fraction in MariaDB (19, plus the fractional digits and their point); MySQL writes 6 fractional digits when they are not zero, none otherwise, MariaDB those of its operands, 6 by a unit of microseconds (`'2024-05-06 07:08:09.5' + INTERVAL 1 SECOND` gives `2024-05-06 07:08:10.500000` in MySQL, `2024-05-06 07:08:10.5` in MariaDB). Of a `JSON`: NULL with a warning in MySQL, error 4078 in MariaDB.
- **Years of an interval from 2^31** (`INTERVAL v YEAR`, `TIMESTAMPADD(YEAR, v, d)`): MariaDB reduces them to 32 bits (`4294967297` adds a year, `4294967295` subtracts one, `4294965272` reaches the year 0), MySQL gives NULL.
- **Microseconds of a compound unit** (`INTERVAL '1.1234567' SECOND_MICROSECOND`): MySQL reads their digits as a number of microseconds (2.234567 seconds), MariaDB their first 6 digits (1.123456 seconds); of 6 digits at most, the same value in both, the digits completed by zeros on the right (`'1.5'` adds 1.5 seconds, `'5'` half a second).
- **The year 0 reached by date and time arithmetic** (`DATE '0001-01-01' - INTERVAL 1 DAY`, by days or a shorter unit): a zero date in MySQL, with its time, NULL in MariaDB.
- **`- INTERVAL n unit + x`**: MariaDB reads it as `x - INTERVAL n unit`, and refuses `~` and `!` before an interval (error 1064); MySQL reads the three as prefix operators of the sum.
- **`TIMESTAMPDIFF` of a string or a number**: MySQL rounds the fractional seconds beyond 6 digits, MariaDB truncates them (`TIMESTAMPDIFF(MICROSECOND, '2024-05-06 00:00:00.1234567', DATE '2024-05-06')` gives -123457 in MySQL, -123456 in MariaDB), for a decimal and a float as well (`20240506000000.123e0` gives -121094 against -121093); a time zone offset is converted by MySQL 8.4, ignored with a warning by MySQL 8.0.11 and MariaDB; the string of a `JSON` (`JSON_EXTRACT('"2024-05-07"', '$')`) is read as a date by MySQL 8.4, NULL in MySQL 8.0.11 and MariaDB.
- **`EXTRACT` of a `TIME`**: MySQL counts all its hours by `HOUR` and its compound units (`EXTRACT(HOUR FROM TIME '100:20:30')` gives 100), gives the same part by the compound units of `DAY` (`DAY_HOUR` 100), and reads the time on the current date by the units of a date; MariaDB counts the hours within a day, the days apart by `DAY` (4 and 4), gives the days and the hours by the compound units of `DAY` (`DAY_HOUR` 404), 0 by `MONTH`, `QUARTER`, `YEAR` and `YEAR_MONTH`, the week of the zero date by `WEEK` (613566757 by mode 0). Both give the sign of the time to every part.
- **`EXTRACT` of a date by the compound units of `DAY` in MySQL**: the day of the month is kept or dropped after the expression (`EXTRACT(DAY_HOUR FROM TIMESTAMP '2024-05-06 07:08:09')` gives 7, 607 in MariaDB, whatever the expression). Kept for a column of a table, the date and time arithmetic, `ADDTIME`, `TIMESTAMP(d, t)`, `STR_TO_DATE`, a user variable, a materialized derived table; dropped for a literal, `CAST`, the functions of the current date and time, `FROM_UNIXTIME`, `LAST_DAY`, `MAKEDATE`, `FROM_DAYS`, `CONVERT_TZ`, `IFNULL`, `COALESCE`, `GREATEST`, `LEAST`, `DATE()`, `MAX`; after their branches for `IF` and `CASE`; after the expression it stands for, for a column of a merged view, of a derived table or of a common table expression; for a subquery that selects a literal, kept in 8.0.11, dropped in 8.4.11 (`crates/probe/cases/extract-forms.txt`, `extract-edges.txt`).
- **`EXTRACT` of a string or a number**: MySQL reads a string as a time by the units of a time, of an hour and of a day (`EXTRACT(MINUTE FROM '2024-05-06')` gives 20, `'2024'` read as `00:20:24`; 0 in MariaDB), as a date by `DAY`; MariaDB reads a time string or a number as a time by `DAY`, the days of its hours (`EXTRACT(DAY FROM 20240506)` gives 84, 6 in MySQL; `EXTRACT(DAY FROM '100:20:30.5')` gives 4, NULL in MySQL). Of 7 fractional digits, MySQL rounds, MariaDB truncates. A date and time of 6 fractional digits at most is read alike by every unit, any value alike by `WEEK`, `MONTH`, `QUARTER`, `YEAR` and `YEAR_MONTH`.
- **Comparisons and tests** (`crates/probe/cases/predicate-grammar.txt`, measured on MySQL 8.0.11 and 8.4.11, MariaDB 10.6.28 and 11.8.9): both dialects read a test (`BETWEEN`, `IN`, `LIKE`, `REGEXP`) tighter than a comparison, on both of its sides (`2 = 2 BETWEEN 1 AND 2` gives 0, `2 = (2 BETWEEN 1 AND 2)`), the high bound of `BETWEEN` as a test (`1 BETWEEN 0 AND 2 IN (1)` gives 0), `IS NULL` on a comparison (`2 = NULL IS NULL` gives 1). MySQL reads a single test after a value, its pattern and its escape character of `LIKE` simple operands (`'2' LIKE 1 + 1` is a syntax error); MariaDB chains the tests from left to right (`1 IN (1) IN (1)`, `'a' LIKE 'a' BETWEEN 0 AND 2`), the bounds of `BETWEEN` tests, the pattern and the escape character at the level of `|`. Towards MySQL, a chained test and a pattern are written between parentheses.
- **`IS TRUE` followed by an operator**: MySQL reads `AND`, `OR` and `XOR` only after `IS TRUE`, `IS FALSE` and `IS UNKNOWN` (`1 IS TRUE = 1` is a syntax error), MariaDB the comparisons and `IS` as well (`(1 IS TRUE) = 1`); neither reads `BETWEEN`, `IN` or `LIKE` after them.
- **Truth value of a `JSON`**: MySQL from 8.0.17 reads a `JSON` of `WHERE`, `HAVING`, `ON`, `NOT`, `AND`, `OR`, `XOR` and `IS TRUE` as compared with 0 (`NOT CAST('false' AS JSON)` gives 0, 1 in 8.0.16), without an entry in the release notes: the change comes from WL#12358, which completes the conditions with `<> 0`, bisected on the images 8.0.11 to 8.0.17. `IF` and `CASE WHEN` read it as a number in every version; MariaDB as a string.
- **Truth value of a fraction**: `WHERE '0.5'`, `WHERE 0.5e0`, `WHERE 0.4` and `WHERE TIME '00:00:00.4'` keep no row in MySQL 8.0.16, a row from 8.0.17 (WL#12358) and in MariaDB; `0.4 XOR 0` gives 0 in MySQL 8.0.16 and MariaDB 10.11.18, 1 from MySQL 8.0.17 and MariaDB 10.11.19, 11.4.13 and 11.8.9 (MDEV-40593, which reports 12.2.2, fixed in 12.3.3 and 13.0.2, not measured). These versions read `NOT (a XOR b)` as `(NOT a) XOR b`: `NOT ((-0.01) XOR 1)` and `(-0.01) XOR 1` both give 1. MySQL rounds the fraction of a time converted to an integer (`CAST(TIME '00:00:00.5' AS SIGNED)` gives 1), MariaDB truncates it (0).
- **Comparison of a `JSON`**: MySQL compares a `JSON` by the rules of JSON (`'b'` equals the JSON string `"b"`, `1` equals `1.0` and differs from `"1"` and from `true`), sorts it in an order of its own (an object, an array, `null`, `true`, the numbers, the strings, `1` and `10` before `2.5` and `1.0`, `"b"` before `"abc"`), converts its value to a number (`true + 0` and `"1" + 0` give 1); `BETWEEN` compares it as its text, with a warning before 8.0.17. MariaDB compares and sorts the text of its `JSON`, of collation `utf8mb4_bin` and coercibility 2. In MySQL, `CONCAT(j)` has that collation and that coercibility, `CAST(j AS CHAR)` the collation of the connection (`utf8mb4_0900_ai_ci`). MySQL stores the text of a `JSON` normalized (`{"a":1}` stored `{"a": 1}`, `2.50` stored `2.5`), MariaDB as written: their texts differ for the same insertion.
- **`IN` of a `JSON` in MySQL**: from 8.0.17, `IN` of a list compares all its values by the rules of JSON when one is a `JSON` (`compare_as_json` and `cmp_item_json` in `Item_func_in::resolve_type`, absent from 8.0.16), without an entry in the release notes; bisected on the images 8.0.11 to 8.0.17. Before, with a warning, a `JSON` as its text against a string (`"b"` differs from `'b'`) and as a number against a number (`true IN (1, 5)` is true). A list of one value is a comparison `=`, alike in every version.
- **Negative zero of a `TIME`**: `TIME '-01:00:00' + INTERVAL 1 HOUR` gives `-00:00:00` in MariaDB 10.6.28 and 11.8.9, `00:00:00` in MySQL 8.0.11 and 8.4.11.
- **Range of `TIME`**: up to `838:59:59` in MySQL, a fraction there an error (`TIME '838:59:59.5'`, a string in the ODBC form); up to `838:59:59.999999` in MariaDB.
- **Temporal strings read by one dialect**: MySQL reads `2024--05-06`, `2024-05-06--`, `2024-05-06 -`, `TIME ':08:09'`, `TIME '.'` and `TIMESTAMP '2024-05-06 -07:08:09'`; MariaDB reads `+2024-05-06` and `2024-05-06T` (`{d '2024-05-06T'}` included).
- **Time zone offset of a date and time literal**: MySQL from 8.0.19 converts it to the time zone of the session (`TIMESTAMP '2024-05-06 01:00:00+02:00'` under `+05:00` gives `04:00:00`), from `-14:00` to `+14:00`, `-00:00` and a zero month or day refused; before 8.0.19, and in MariaDB, error 1525, and a string in the ODBC form. `TIMESTAMP '2024-05-06 07+02:00'` gives `07:02:00` everywhere, the sign read as a separator.
- **Zero dates of the literals**: `date NULL` in MariaDB, `date NOT NULL` in MySQL; the SQL modes `NO_ZERO_DATE` and `NO_ZERO_IN_DATE` act alike, but the default modes differ: those of MySQL refuse the zero dates, those of MariaDB accept them.
- **Negative zero of the floats**: MySQL writes it `-0`, MariaDB `0` from the fix of MDEV-38670, whatever the expression: the literal `-0e0`, `-(f - f)`, `CONCAT`, `CAST` to `DOUBLE`, `FLOAT`, `CHAR` or `BINARY` (`0x2D30` against `0x30`), `GREATEST(-0e0, -1)`, `ROUND(-0.4e0)`, `CEILING(-0.5e0)`; the string `'-0'` to `DOUBLE` gives `-0`, to `TIME` `-00:00:00`, in MySQL. Both compare it equal to 0, and `-0e0 + 0` gives `0` in both. MariaDB writes `-0` as MySQL before the fix, released in 10.6.26, 10.11.17, 11.4.11, 11.8.7 and 12.3.2 (by the ticket): `-0` in 10.6.16 to 10.6.18, 10.7.1 to 10.11.16, 11.0.2 to 11.3.2 and 11.5.2 to 11.7.2, `0` in 10.6.28, 10.11.17 to 10.11.19, 11.4.11 to 11.4.13 and 11.8.7 to 11.8.9. The conversion of a string that `GREATEST` writes towards MySQL, `'-0' + 0e0`, gives `0`, where MariaDB before the fix gives `-0` for `GREATEST('-0', -1)` (`crates/probe/cases/negative-zero.txt`, each local image, MySQL 8.0.11 to 9.3.0, MariaDB 10.5.29 to 11.8.9).
- **`LEAST` and `GREATEST` of a string and a number** compare them as strings in MySQL, as numbers in MariaDB: `LEAST('300', 2147483648)` gives `2147483648` in MySQL 8.0.11 and 8.4, `300` in MariaDB 10.6 and 11.8. A date with a string compares as dates in both, the result a `VARCHAR` in MySQL, a nullable `DATE` in MariaDB; a time with a string or a number compares as strings in MySQL, as times in MariaDB, of the fractional digits of the string (`LEAST(t, '9:00:00.5')` is a `TIME(1)`). An `ENUM` or a `SET` with a number compares as strings in MySQL, by its index in MariaDB. A `NULL` literal among integers or decimals makes the result a `DOUBLE` in MariaDB only. A `YEAR` with an integer gives an `INT` in MySQL, a `DECIMAL` in MariaDB; a `BIT` with a `BIT`, an `INT UNSIGNED` in MySQL, a `BIT` in MariaDB.
- **Metadata of a `JSON` column of MySQL**: a prepared statement describes it as a `LONGTEXT` (`MYSQL_TYPE_BLOB`, 4294967295 bytes), the result of a query as a `JSON` (`MYSQL_TYPE_JSON`, binary collation); `SHOW COLUMNS` names it, for a temporary table and a view as well. MariaDB declares its `JSON` as a `LONGTEXT` (next entry).
- **Collation of a column in the metadata**: a prepared statement, as the result of a query, gives a string the collation of the results of the connection, `utf8mb4_0900_ai_ci` in MySQL 8.4.11 and `utf8mb4_unicode_ci` in MariaDB 11.8.9 for columns of `utf8mb4_bin`, `utf8mb4_unicode_ci` and `latin1_general_cs` alike (the server reports the character set of the results, `character_set_results`, by its default collation). `SHOW FULL COLUMNS` gives the collation of each column, for a temporary table and a view as well: the catalog of the plan reads it there, one more query per table of the query.
- **`JSON` column of MariaDB**: a `LONGTEXT` for its metadata, of collation `utf8mb4_bin`, with the check ``json_valid(`j`)``. The functions of MariaDB read a column as a `JSON` when its check is a call of `json_valid`, of any argument (`k JSON CHECK (json_valid(g))` as well), a column of a view through its table, and as a string a column of a check of its own (`JSON CHECK (JSON_LENGTH(j) < 5)`, `json_valid(f) AND ...`) or of a check of the table (`CONSTRAINT c CHECK (json_valid(m))`). `SHOW CREATE TABLE` writes the check last on the line of the column, after its comment; quotes a name by backticks, by double quotes under `ANSI_QUOTES`, not at all when `sql_quote_show_create` is off and the name needs no quotes; doubles the quote of a comment (`'it''s'`) and escapes by a backslash that of a default (`'x\'y'`) and a backslash (`'a\\'`), under `NO_BACKSLASH_ESCAPES` as well.
- **Type of `UNIX_TIMESTAMP`**: `INT(11)` in MySQL 8.0.11, `BIGINT` in 8.0.27 and later, `BIGINT(17)` in MariaDB.
- **`REGEXP`, `SOUNDS LIKE` and `MEMBER OF`** (`crates/probe/cases/regexp-grammar.txt`): the pattern of `REGEXP` and the right operand of `SOUNDS LIKE` at the level of `|` in both dialects, where MySQL reads the pattern of `LIKE` as a simple operand; `NOT SOUNDS LIKE` and `NOT MEMBER OF` are syntax errors. `MEMBER OF` of MySQL takes `OF` as optional (`1 MEMBER ('[1]')`) and a simple operand between parentheses (`MEMBER OF ('[1]' + 0)` is a syntax error). `SOUNDS` after a value always opens `SOUNDS LIKE`, and `MEMBER` `MEMBER OF` from MySQL 8.0.17: `SELECT 1 sounds` and `SELECT 1 member` are syntax errors there, `AS` required (`crates/probe/cases/reserved-words.txt`).
- **Type of `REGEXP` in MySQL**: a `DOUBLE(21, 0)` in 8.0.11, as `REGEXP_LIKE`, a `BIGINT(21)` in 8.0.12 and 8.0.13, an `INT` from 8.0.14 (`set_data_type_longlong` in `Item_func_regexp_like` from 8.0.12, without an entry in the release notes). The `DOUBLE` of 8.0.11 keeps its number of fractional digits through arithmetic (`(s REGEXP 'b') / 3` is a `DOUBLE(22, 4)`, a `DECIMAL` from 8.0.12); `NOT REGEXP` is an `INT` in every version.
- **`REGEXP` of a binary string in MySQL**: 8.0.11 reads it otherwise than its bytes (`CAST('aBc' AS BINARY) REGEXP CAST('B' AS BINARY)` gives 0, `CAST(CONVERT('é' USING utf8mb4) AS BINARY) REGEXP '^.$'` 1); 8.0.12 to 8.0.21 byte by byte, case-sensitive, a character string with it in its character set (`CONVERT('é' USING utf8mb4) REGEXP CAST('^..$' AS BINARY)` gives 0, 1 in MariaDB, which reads the string as its bytes); from 8.0.22, refused with a character string, error 3995 (Bug #98950), two binary strings read byte by byte. A number with a binary string goes through in 8.0.22 (`123 REGEXP CAST('2' AS BINARY)` gives 1).
- **Line terminators of `REGEXP`** (`crates/probe/cases/regexp-operator.txt`, `regexp-translation.txt`): ICU ends a line at CR, LF, CR LF, VT, FF, NEL, LS and PS, for `.`, `$`, `\Z`, and `^` and `$` of `(?m)` (between CR and LF too); PCRE2 of MariaDB at LF. `(*ANY)` gives those of ICU to PCRE2; `(?d)`, the Unix lines of ICU, scoped and negatable in MySQL 8.0.11 and 8.4.11, gives that of PCRE2 to ICU, except for `\Z`. The `.` of `(?s)` reads CR LF as one character in ICU, even after `(?d)`: `(?s)^a.\nb$` does not match `a\r\nb`, nor does `(?s)^a[\s\S]b$`. `\R` is the same in both, CR LF read at once.
- **Classes of `REGEXP`** (`crates/probe/cases/regexp-classes.sql`): `\d`, `\D`, `\v`, `\V`, `[:digit:]`, `[:cntrl:]`, the ranges, and the general categories other than `L`, `Lu`, `Ll`, `Lt`, `M` and `Mn` under case insensitivity, match the same characters in both libraries; `\s`, `\h`, `[:space:]` and `[:blank:]` too, U+180E (MONGOLIAN VOWEL SEPARATOR) aside, a space for PCRE2 only. `\w` of ICU is `[\p{L}\p{Nl}\p{M}\p{Nd}\p{Pc}\x{200C}\x{200D}\x{24B6}-\x{24E9}\x{1F130}-\x{1F149}\x{1F150}-\x{1F169}\x{1F170}-\x{1F189}]` for PCRE2. `[:alpha:]` is `Alphabetic` for ICU, `L` for PCRE2; `[:punct:]` of PCRE2 adds the ASCII symbols `` $+<=>^`|~ ``. Under case insensitivity, ICU closes a property over the case of its characters: `\p{L}` takes U+0345, `\p{Lu}` and `\p{Ll}` take all the cased letters, `\p{M}` takes `ι`, `Ι` and U+1FBE.
- **Case folding of `REGEXP` in ICU** (`crates/probe/cases/regexp-folding.txt`): under a collation `_ci`, or `(?i)` under any collation, ICU compares a run of literal characters by the full folding of the case: `ss` matches `ß`, `ß` matches `ss`, `ſs` and `SS`, `ffi` matches `ﬃ`, `ﬀi` and `fﬁ`, `İ` matches `i̇`. A quantifier takes the last character of a run off it (`ss+` does not match `ß`, `sss+` matches `ßs`), a character that folds into several ones keeping its folding alone (`ß+`, `(ß)`, `ß{1}` match `ss`); a comment, `\Q...\E` and an escape (`\x73`) keep the run, a flag, a group, a class, an alternation, an anchor and a lookaround cut it (`s(?:)s` does not match `ß`). A class matches single characters only (`[ß]` matches `ß` and `ẞ`, not `ss`), as a character alone of a folding of one character; ICU then matches `ΐ` (U+0390) with U+1FD3, `ΰ` (U+03B0) with U+1FE3 and `ﬅ` with `ﬆ`, PCRE2 not. A backreference compares by the full folding: `(ß)\1` matches `ßss`. PCRE2 compares each character with the characters of its case.
- **Unicode of ICU and PCRE2**: each library has its own version, a code point of another category in each one: MySQL 8.0.11 reads U+111C9 as a mark, the Georgian letters U+10D0 to U+10FF as `Lo`, U+1CF2 and U+1CF3 as marks, U+166D as a symbol, and lacks the Georgian capitals (Mtavruli) and U+A7C4 to U+A7C6 in its case folding; ICU of MySQL 8.4.11 reads U+1171E as `Mc`, PCRE2 of MariaDB 10.6.28 and 11.8.9 as `Mn`. the images of MariaDB link the PCRE2 of their system (`libpcre2-8` 10.39 of Ubuntu in 10.6.28, 10.42 in 11.8.9), whose `\w` and scripts follow its version. The translation keeps these limits.
- **Syntax of `REGEXP`** (`crates/probe/cases/regexp-features.txt`, `regexp-syntax.txt`): ICU refuses `}` out of a quantifier, `a{2 }`, `{,2}`, the empty pattern (error 3685), the verbs `(*...)`, `\k{x}` and `(?'x'...)`, which PCRE2 reads (its reading of `{` changes in 10.43). PCRE2 refuses a lookbehind of a variable length (`(?<=a{1,2})`), which ICU reads up to a bound. An escaped ASCII punctuation, and `\é`, is the character itself in both; `]` alone, first in a class, and `-` first or last in a class, too.
- **Collation of an introduced string** (`crates/probe/cases/literals-collations.txt`): the default collation of its character set in the server, whatever the collation of the connection. `_utf8mb4'a'` takes `utf8mb4_0900_ai_ci`, NO PAD, in MySQL, `utf8mb4_general_ci` in MariaDB to 11.3, `utf8mb4_uca1400_ai_ci` from 11.4 (set by its packages); `_utf8mb3'a'`, `_ucs2'a'`, `_utf16'a'` and `_utf32'a'` take `uca1400_ai_ci` from MariaDB 11.5.1 (MDEV-25829), `general_ci` elsewhere. A national string keeps `utf8mb3_general_ci` in every version, even where `_utf8mb3'a'` takes another collation. `CHARSET(_utf8'a')` gives `utf8` in MySQL 8.0.11 and 8.0.28, `utf8mb3` in 8.4.11 and in MariaDB. The coercibility of a string literal is 4, 5 in MariaDB 11.5.2, 6 from 11.6.2.
- **Name of a column of adjacent strings** (`crates/probe/cases/literals-names.sql`): MySQL names `'a' 'b'`, `N'a' 'b'`, `_latin1'a' 'b'` and `_binary'a' 'b'` after their first string (`a`), MariaDB after their value (`ab`), measured on MySQL 8.0.11 and 8.4.11, MariaDB 10.6.28 and 11.8.9 (`_binary'a' 'b'` on 8.4.11 and 11.8.9); an alias keeps the name between the dialects. MariaDB names them after their first string as well before the fix of MDEV-33460, a row of `VALUES` and the column of a derived table alike (construct `string_value_name`, measured on each local image of MariaDB): `a` on 10.6.3 to 10.6.17, 10.7.1 to 10.11.7, 11.0.2 to 11.0.5, 11.1.2 to 11.1.4, 11.2.2, 11.2.3 and 11.3.2, `ab` on 10.5.29, 10.6.18 to 10.6.28, 10.11.8 to 10.11.19, 11.0.6, 11.1.5, 11.1.6, 11.2.4 to 11.2.6 and from 11.4.2. The ticket gives the fix to 10.5.25, 10.6.18, 10.11.8, 11.0.6, 11.1.5 and 11.2.4, the release notes do not cite it, and the conformance suite found it on the images added (`docs/sources/mariadb/MDEV-33460.md`).
- **Hexadecimal and bit literals** (`crates/probe/cases/literals-hex.txt`, `literals-hybrid.txt`, `literals-hex-long.txt`, `literals-hex-functions.txt`): `X'41'` is a hybrid in MySQL, a byte string in MariaDB (`X'41' + 0` gives 65, 0 in MariaDB; `X'' + 0` an `INT UNSIGNED`, a `DOUBLE` in MariaDB); a bit literal reads as a signed integer in MySQL (`b'101' + 0` is an `INT`, an `INT UNSIGNED` in MariaDB). Read as a number beyond 8 bytes, a byte before the last 8 not zero: 2^64 - 1 until MySQL 8.0.26, 0 from 8.0.27, with the warning 1292 (`Item_hex_string::val_int` returns -1 then 0, without an entry in the release notes), the last 8 bytes in MariaDB. A unary minus, `ABS`, `CEIL`, `FLOOR`, `ROUND` and `TRUNCATE` compute a `DOUBLE` in MySQL, an integer in MariaDB (`ROUND(0x41, -1)` gives 60, 70 in MariaDB); `CONV`, `BIN` and `OCT` read a string in MariaDB (`BIN(0x41)` gives `0`). As bytes, the comparisons with strings, `LIKE`, `CAST` to a string and the string functions read a literal of 11 bytes alike.
- **Hexadecimal literals as results of the conditional functions** (`crates/probe/cases/literals-hex-results.txt`): read as a number, MySQL reads a hybrid as a number in `CASE`, `IF` and `NULLIF`, whatever the other results (`IF(1, 0x41, 'b') + 0` gives 65), as a string in `IFNULL` and `COALESCE` (0); MariaDB as a string, then from 10.11.19, 11.4.13 and 11.8.9 as a number when all the results are hybrids or `NULL` (`IF(1, 0x41, 0x42) + 0` gives 65, 0 in 11.8.8), a change released with MDEV-38061, which describes another fix. As a condition (`WHERE IF(1, 0x41, 0x42)`), MySQL keeps the row, MariaDB 11.8.9 reads NULL.
- **Names inside an expression of `ORDER BY`, `GROUP BY` and `HAVING`** (`crates/probe/cases/alias-references.sql`, measured on each local image of MySQL, 8.0.11 to 9.3.0, and of MariaDB, 10.5.29 to 11.8.9): a column of the source before an alias of the select list, in both dialects, an alias first for a name alone in `ORDER BY`; `HAVING` reads a grouping column first, even when an alias has its name in MySQL (warning 1052), an ambiguous name in MariaDB (error 1052), the alias of an aggregate function or of the column itself (`SELECT b AS B ... GROUP BY b HAVING b`) and a qualified name (`HAVING t.b`) aside. MariaDB refuses an alias of an aggregate function inside an expression of `ORDER BY` (`ORDER BY s + 0`, error 1247), in a query between parentheses too, and reads it in `HAVING`; MySQL reads both, before 8.0.29 otherwise (next entry). MariaDB from 10.6 names the clauses otherwise in its messages (`in ORDER BY`, `in order clause` in 10.5.29).
- **The alias of an aggregate function inside an expression of `ORDER BY` or of a window** is read by MySQL 8.0.11 to 8.0.28 as one value for all the rows: `SELECT a % 2 AS x, COUNT(*) AS n ... GROUP BY x ORDER BY n + 0 DESC, x` keeps the rows in the order of `x`, `ORDER BY -n` alike, `RANK() OVER (ORDER BY n + 0)` gives 1 to every row, in the `WINDOW` clause too; the aggregate function written in its place sorts in every version. Read as the function from 8.0.30 (measured on each local image, 8.0.29 having none; Bug #32695670 of 8.0.29). Two groups of the same sum hid it in the first measures (section 6.1).
- **A window function read through its alias inside an expression of `ORDER BY`** is computed again for the sort by MySQL 8.0.16 to 8.0.28, and the result shows the values computed again: `ROW_NUMBER() OVER (ORDER BY b) AS r ... ORDER BY r + 0` numbers 1, 2, 4 three rows, `RANK` and `ORDER BY -r`, `CONCAT(r)` or a named window alike; `SUM(b) OVER (ORDER BY id)` gives 10, 50, 100 for 10, 40, 60 up to 8.0.26 only. The alias alone and the window function written in `ORDER BY` give the right values in every version. Fixed in 8.0.29 (Bug #32695670: "Aliases to `SELECT` list items in `ORDER BY` which were part of expressions were not resolved in the same way as standalone aliases"), measured from 8.0.30, 8.0.29 having no image.
- **An aggregate function of an alias of an aggregate function** (`SELECT SUM(b) AS s ... HAVING SUM(s) > 30`): read by MySQL up to 8.0.26 and by MariaDB 10.5.29 to 11.8.9, error 1111 from MySQL 8.0.27 (Bug #13633829, Bug #30106081: "Now the server checks explicitly for such illegal references").
- **Aliases inside a window** (measured on each local image of MySQL, 8.0.11 to 9.3.0, and on MariaDB 10.5.29 to 11.8.9): MariaDB reads a name alone in the `PARTITION BY` and the `ORDER BY` of a window, of the `WINDOW` clause and of a window of `ORDER BY` as an alias first, before a column of the same name (`SELECT a AS b, ROW_NUMBER() OVER (ORDER BY b)` sorts on `a`), an alias written after the window too; MySQL reads it as a column of the source only (error 1054 for an alias; a column that an alias names an error too in 8.0.11 to 8.0.13, Bug #27808099, fixed in 8.0.14: "failed with Unknown field in window order by even when the column was found in the table"). Inside an expression (`OVER (ORDER BY b + 0)`, `-b`, `(SELECT b)`), both read a column of the source first, then an alias; MariaDB refuses there an alias of an aggregate function (error 1247). Neither reads an alias in the arguments of a window function (`LAG(x)`, error 1054), nor the alias of a window function in a window (error 4016 in MariaDB, 1054 alone and 3595 in an expression in MySQL).
- **`ORDER BY` of a grouped query with window functions in MariaDB** (`crates/probe/cases/grouped-window-order.sql`, measured on each image of MySQL 8.0.11 to 9.3.0 and of MariaDB 10.5.29 to 11.8.9): MariaDB takes the order of the grouping for an `ORDER BY` that is a prefix of `GROUP BY`, constants aside, in either direction, a key read through its alias, its position, its table or between parentheses, and drops the sort when an index gives that order (the primary key, a unique or a plain index, the prefix of a composite key; `EXPLAIN` shows no `filesort` above `window_functions_computation`). The rows come out in the order of the last sort of the windows, and `LIMIT` keeps other rows: with the primary key `id`, `SELECT id, ROW_NUMBER() OVER (ORDER BY id DESC) AS r FROM t GROUP BY id ORDER BY id LIMIT 2` gives 4 and 3, and 1 and 2 in MySQL. A key without index keeps the order, a temporary table sorting the groups after the windows. MDEV-30890, closed as incomplete, reports it with `HAVING` in 10.4. `ORDER BY id IS NULL, id` loses the order as well in 10.5.29 to 10.11.16, 11.0.2 to 11.3.2 and 11.5.2 to 11.7.2, and keeps it in 10.11.17 to 10.11.19, 11.4.11 to 11.4.13 and 11.8.7 to 11.8.9. A last key on an item with a window function (`ORDER BY id, 2`) keeps the order in every version measured, `COUNT(*) OVER ()` included: from MySQL, the emitter adds it to an `ORDER BY` of grouping keys and constants alone (rule `order.grouped-windows`, **[decided autonomously]**). A derived table would sort the rows too, but MariaDB and MySQL 8.0.11 to 8.0.13 refuse one that reads the enclosing query (error 1054). From MariaDB, the query keeps the text written, which its server sorts or not according to its indexes.
- **Limits of a query between parentheses in MySQL** (`crates/probe/cases/parenthesized-limits.sql`): an outer `LIMIT` overrides the inner one up to 8.0.30 (Bug #82560 answered it as documented, Bug #103954 fixed it in 8.0.31 by WL #11350), and drops the inner `ORDER BY` up to 8.0.18; an outer `OFFSET` over an inner `LIMIT` counts from the start of the inner rows from 8.0.31 to 9.3.0 (`(SELECT a FROM lim ORDER BY a LIMIT 3) LIMIT 5 OFFSET 3` gives 4, 5, no row in MariaDB), which no ticket of bugs.mysql.com reports; `(SELECT a FROM lim ORDER BY a DESC) LIMIT 2` gives the 5 rows, ascending, from 8.0.19 to 8.0.25; up to 8.0.18, an outer `ORDER BY` sorts a set operation between parentheses before its `LIMIT` (`(SELECT a FROM lim UNION SELECT 6 LIMIT 2) ORDER BY 1 DESC` gives 6, 5). A derived table reads by the standard in every version, but MariaDB drops the `ORDER BY` of a derived table without `LIMIT` (`SELECT * FROM (SELECT a FROM lim ORDER BY a DESC) AS d LIMIT 2` gives 1, 2, and 5, 4 in MySQL).
- **Names of an `ORDER BY` after a `SELECT` between parentheses in MySQL** (`crates/probe/cases/alias-references.sql`): without `ORDER BY` or `LIMIT` between the parentheses, read as those of an `ORDER BY` of the `SELECT` up to 8.0.30, as in MariaDB, as the columns of the result from 8.0.31 (WL #11350) to 8.0.41, 8.1.0 to 8.4.4 and 9.0.1 to 9.2.0, and as those of the `SELECT` again from 8.0.42, 8.4.5 and 9.3.0, which no release note mentions. `(SELECT id, a AS b FROM t) ORDER BY b + 0` sorts on the column `b` of the table, then on the alias; in between, `(SELECT id FROM t) ORDER BY a` is refused (error 1054), `ORDER BY t.b` too (error 1250 in 8.0.31 and 8.0.32, 1109 after), a name of the column of an item is read as well as its alias (`(SELECT a AS x, MAX(b) AS m FROM t GROUP BY a) ORDER BY -a`), an aggregate function of the `ORDER BY` is refused (`ORDER BY -MAX(b)`, error 1054), and an expression of the alias of a grouping key that is an expression, in a block with aggregate functions, sorts the rows otherwise (`(SELECT a % 2 AS x, COUNT(*) AS n FROM t GROUP BY x) ORDER BY -x` gives 0 before 1, `x + 0 DESC` too; right with `x DESC`, with a key that is a column, without aggregate function). The names of a subquery of that `ORDER BY` are read as the columns of the result from 8.0.31, after 8.0.42, 8.4.5 and 9.3.0 too (`ORDER BY (SELECT b)`). With an `ORDER BY` or a `LIMIT` between the parentheses, every version of MySQL reads the columns of the result (next entry for MariaDB). MariaDB refuses a `WITH` between parentheses (error 1064).
- **Names of an `ORDER BY` after a query between parentheses with its own `ORDER BY` or `LIMIT` in MariaDB** (`crates/probe/cases/parenthesized-order.sql`, measured on each local image, 10.5.29 to 11.8.9, `docs/sources/mariadb/MDEV-29681.md`): read in the context of the query between parentheses, which the parser wraps into a derived table, in 10.6.16, 10.7.8 to 10.11.6, 11.0.2 to 11.0.4, 11.1.2 to 11.1.3 and 11.2.2, fixed in 10.6.17, 10.11.7, 11.0.5, 11.1.4 and 11.2.3 (MDEV-29681, whose title only names a crash). A name alone or a position reads the column of the result; any other key does not: `(SELECT id, a AS b FROM t LIMIT 3) ORDER BY -b` keeps the order of the rows between parentheses, or another, an alias without column of the same name too (`-x`), as soon as the query between parentheses is materialized (`LIMIT`, `DISTINCT`, `GROUP BY`); with an `ORDER BY` alone, `-b` sorts on the column `b` of the table; error 1054 over a set operation (`Unknown column 'b'`), 1052 over a join, or no defined order (11.1.2, 11.1.3 and 11.2.2). An expression of the alias of a window function (`ORDER BY -r`) stops the server (signal 11), the alias alone does not. A subquery of that `ORDER BY` sorts the rows in no defined order in every version, fixed or not (`ORDER BY (SELECT -b)`). The same query from a derived table reads the columns of the result in every version, subquery and window function included.
- **Set operation between parentheses as a right operand** (`SELECT 1 UNION (SELECT 2 UNION SELECT 3)`, `crates/probe/cases/nested-set-operations.sql`, measured on each local image): MySQL refuses it with error 1064 from 8.0.11 to 8.0.18, with 1235 from 8.0.19 to 8.0.30, and accepts it from 8.0.31 (WL #11350, `docs/sources/mysql/8.0.31.md`); every MariaDB from 10.5.29 accepts it. The left operand between parentheses and a single query between parentheses go through in every version. The construct was first dated 8.0.22, from the page of the manual on parenthesized query expressions; the release notes and the measures on each image date it 8.0.31.
- **`ARRAY` and `MEMBER`**: reserved in MySQL 8.0.17 and 8.0.18 only (`SELECT 1 AS member` is a syntax error there), names before and after, as in MariaDB (`crates/probe/cases/reserved-words.txt`, measured on 8.0.11, 8.0.16 to 8.0.20, 8.0.22, 8.0.28 and 8.4.11, MariaDB 10.6.28 and 11.8.9).

LIMIT` (Bug #79340). Every server counts every row with an `ORDER BY` or a `UNION` (`crates/probe/cases/select-options.sql`, measured on each local image).
- **Options of the first `SELECT` between parentheses**: MariaDB refuses `HIGH_PRIORITY`, `SQL_BUFFER_RESULT`, `SQL_CALC_FOUND_ROWS`, `SQL_NO_CACHE` and `SQL_CACHE` in a `SELECT` between parentheses followed by `ORDER BY` or `LIMIT` (error 1234), in every version measured, 10.5.29 to 11.8.9; MySQL reads them there.
- **Locking clauses of each dialect** (`crates/probe/cases/locking.sql`, measured on each local image, MySQL 8.0.11 to 9.3.0, MariaDB 10.5.29 to 11.8.9): MySQL reads `FOR SHARE`, `OF` with the names of the tables of the block as the block names them (error 3568 for the table of an alias, or a name outside the block), a database before the name too, a common table expression among them, several clauses each on its own tables (error 3569 for a table in two clauses, and for a derived table, "appears in multiple locking clauses"), `NOWAIT` and `SKIP LOCKED`, and `LOCK IN SHARE MODE` without option (error 1064). MariaDB reads one clause, without `FOR SHARE` nor `OF` (error 1064), `WAIT n` of an integer, a decimal, an approximate or a hexadecimal number (`WAIT 0x2`), `SKIP LOCKED` from 10.6.0 (error 1064 on 10.5.29), and `OF` as a name (`SELECT 1 AS of`), which MySQL reserves. Both read a clause on a block without table (`SELECT 1 FOR UPDATE`), in a subquery, a derived table and a common table expression, and lock the last operand of a set operation by a clause after it.
- **Rows locked next to a query between parentheses** (`crates/probe/cases/locking-scope.sql`, `trx_rows_locked` measured on each local image, MySQL 8.0.11 to 9.3.0, MariaDB 10.5.29 to 11.8.9; `locking` module): a clause after the outer `ORDER BY` or `LIMIT`, or right after the parentheses, locks the rows of the query between them when the server joins the outer clauses to those of that query, none otherwise, the outer clauses making a block of their own, without table. MariaDB joins them when the query between parentheses has no `LIMIT` of its own and the two sides do not both have an `ORDER BY` (`(SELECT a FROM t LIMIT 2) FOR UPDATE` locks no row); MySQL up to 8.0.17 joins an outer `LIMIT` alone, and an outer `ORDER BY` over a query without `ORDER BY`, `LIMIT` nor set operation; 8.0.18 every outer clause but a `LIMIT` over a set operation with its own `LIMIT`, which 8.0.19 to 8.0.30 refuse (error 1235); 8.0.31 every one. The release notes say nothing of it.
- **A locking clause at the end of a query between parentheses followed by a `LIMIT` without `ORDER BY`** (`(SELECT a FROM t FOR UPDATE) LIMIT 1`) locks no row in MySQL up to 8.0.18, the clause dropped (Bug #30521098, fixed in 8.0.19 by its release notes, measured on each local image); it locks the rows read in MariaDB and in MySQL from 8.0.19.
- **MySQL 8.0.19 to 8.0.25 give every row of a locked `SELECT` between parentheses with its own `ORDER BY`** before an outer `LIMIT` without `ORDER BY`: `(SELECT id FROM t ORDER BY id) LIMIT 2 FOR UPDATE` and `(SELECT id FROM t ORDER BY id FOR UPDATE) LIMIT 1` give the 5 rows of `t` and lock them all, 2 rows and 1 row from 8.0.26, as before 8.0.19 and in MariaDB (`crates/probe/cases/locking-scope.sql`, measured on each local image). With a `LIMIT` between the parentheses, an outer `ORDER BY`, or without `ORDER BY` between them, the `LIMIT` applies in every version. The release notes of 8.0.19 and 8.0.26 say nothing of it.
